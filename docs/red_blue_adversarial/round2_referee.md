> 日期：2026-03-30

## 一、进步评估

### 1.1 红队进步

**显著进步：**

- 第一轮的最大问题是"发现问题强、解决问题弱"。第二轮红队针对蓝队 16 条规则逐条给出了具体的反制代码和数学推导，质量大幅提升。
- 裁判第一轮指出的盲区（x-stainless-* 头、连接复用、Origin/Referer、OAuth 时序、HTTP/2 指纹）在第二轮全部覆盖。尤其是 x-stainless-* 头的补全非常细致，包括了 OS/arch/runtime 等所有子字段。
- `count_tokens` 伴随流量方案务实可行，比第一轮的"等逆向完再说"态度有本质进步。分三阶段的策略（安全的 count_tokens -> usage 查询 -> 完整遥测）风险递增，是合理的工程决策。
- 最出色的部分是数学推导：红队利用蓝队公开的评分模型，逐层计算加权分数，得出第一阶段修复后总分 42.75 < 50（ALLOW 阈值），这是一次"白盒攻击"的教科书式操作。
- 对 SSE 中继延迟的反驳论证有说服力（TCP 层 ACK 由内核自动完成，应用层消费模式在服务端视角不可见），展现了对网络协议栈的深层理解。

**仍需改进：**

- HTTP/2 指纹部分虽然覆盖了，但方案仅停留在"蓝队如果部署我们再应对"的被动姿态。没有主动研究 hyper 的 HTTP/2 参数自定义能力。
- BoringSSL 集成方案（hyper-boring）仍是"路径指引"而非实际 PoC。两轮了，这个核心方案的可行性仍未验证。
- 对内容画像（BEH-05）的反制方案最弱。"注入代码上下文味道"的方案自己也承认"风险高，建议作为最后手段"。这实际上是承认无能为力。

### 1.2 蓝队进步

**显著进步：**

- 第一轮过度依赖 clewdr 的"低级错误"（billing 注入、ClewdR 命名），裁判明确批评了这一点。第二轮蓝队做了关键的战略调整：假设红队已完成第一阶段修复，在此基础上构建第二代检测体系。这是正确的思维方式。
- 新增的检测维度质量高：HTTP/2 指纹 (NET-05)、请求内容画像 (BEH-05)、会话主题一致性 (BEH-06)、Stainless SDK 头 (REQ-06) 四个新规则都击中了红队的真实盲区。
- 最大的创新突破是**主动探测体系**（PROBE-01/02/03）。从被动检测升级为主动出击，这是质的飞跃：
  - tool_use 探针利用了反代架构的根本矛盾（下游客户端无法执行 Claude Code 工具）
  - 响应水印实现了跨会话关联追踪
  - 蜜罐账户直接从源头收集反代指纹
- 权重重分配（请求层从 0.30 降到 0.20，行为层从 0.20 升到 0.25，新增 content 和 graph 层各 0.10）是对红队击杀 REQ-01/REQ-05 后的合理应对。
- BEH-03v2 的语义级验证是对第一轮的精准加固：不仅检查"有没有"伴随流量，还校验 count_tokens 的 body hash 与后续 chat 是否一致。这直接攻击了红队第二轮的 count_tokens 方案。

**仍需改进：**

- GRAPH-01 的工程复杂度被严重低估。实时维护一个全局实体关联图（IP x Cookie x Token x ClientID x Org），在高并发 API 环境下的性能开销和存储成本是巨大的。蓝队对此只给了一段 networkx 代码，完全是单机 demo 级别。
- SSE 中继检测 (NET-06) 的前提假设存疑。如红队所指出的，服务端无法直接观察客户端的 SSE 消费行为。蓝队假设可以通过比较 server_timestamp 和 client_receive_timestamp 来检测中继延迟，但 client_receive_timestamp 从何获取？蓝队只能观察到自己的发送时间和 TCP ACK 时间，这与客户端的真实接收时间不同。
- 误报率控制不够严谨。新增的 6 个维度中，BEH-06（主题一致性）的误报率高达 5-8%，BEH-05（内容画像）3-5%。如果这些规则联合触发，误报的累积效应可能超出可接受范围。

### 1.4 新的跑偏迹象

- **红队的数学推导有过度自信的风险**：红队基于蓝队第一轮的评分模型推导出 42.75 分，但蓝队第二轮已经重新调整了权重和规则。红队的数学推导只攻破了蓝队 v1 评分模型，但蓝队已迭代到 v2。这种"打上一代"的策略在对抗中很常见，但红队自评中完全没有考虑蓝队第二轮可能的进化。
- **蓝队的 PROBE-01 存在伦理/产品风险**：在 API 响应中注入探针工具调用会影响正常用户体验。如果误触发，真实 Claude Code 用户的工作流会被一个莫名其妙的 `get_workspace_info` 工具调用打断。蓝队承认"只对灰色地带 50-70 分的会话探测"，但这仍然会影响落在灰区的正常用户。
- **蓝队的零宽字符水印 (PROBE-02) 过于脆弱**：红队只需一行代码（strip 零宽字符）即可完全失效。蓝队虽然提到"移除零宽字符本身可以成为检测信号"，但正常的文本处理库也可能移除这些字符，误报风险高。

## 二、攻防焦点分析

### 2.1 红队的数学推导（总分 42.75 < 50）是否站得住脚？

**结论：对蓝队 v1 模型成立，但被蓝队 v2 模型击穿。**

红队的推导过程本身是严谨的：

```
NET: max(50, 0, 60, 0) * 0.25 = 60 * 0.25 = 15.0
REQ: max(0, 20, 0, 10, 0) * 0.30 = 20 * 0.30 = 6.0
BEH: max(0, 60, 70, 10) * 0.20 = 70 * 0.20 = 14.0
AUTH: max(0, 25, 0) * 0.15 = 25 * 0.15 = 3.75
STAT: 40 * 0.10 = 4.0
总分: 42.75
```

但蓝队 v2 新增了多个维度，重新计算：

```
NET: max(50[NET-01], 0[NET-02], 60[NET-03], 0[NET-04v2], 75+[NET-05 HTTP/2]) * 0.25
    = 75 * 0.25 = 18.75  (NET-05 红队完全未覆盖)
REQ: max(0, 20, 0, 10, 0, 40+[REQ-06 stainless头第一轮忽略]) * 0.20
    = 40 * 0.20 = 8.0  (红队在第二轮补了 stainless 头，但蓝队加了版本一致性校验)
BEH: max(0, 60, 35+[BEH-03v2 语义校验], 10) * 0.25
    = 60 * 0.25 = 15.0  (权重从 0.20 升到 0.25)
AUTH: max(0, 25, 0) * 0.10 = 25 * 0.10 = 2.5
Content: max(70+[BEH-05 内容画像]) * 0.10 = 70 * 0.10 = 7.0  (新增层)
Graph: max(50+[GRAPH-01]) * 0.10 = 50 * 0.10 = 5.0  (新增层)
总分: 18.75 + 8.0 + 15.0 + 2.5 + 7.0 + 5.0 = 56.25 -> MONITOR_AND_PROBE 区间
```

即使红队第二轮补上了 stainless 头（REQ-06 降到 0-15），内容画像 (BEH-05) 和 HTTP/2 指纹 (NET-05) 仍然贡献了显著分数。**红队的数学推导只打赢了蓝队 v1，但在对抗场景中蓝队会同步进化。**

不过，需要注意的是，上述重新计算的部分数值也有不确定性（比如红队第二轮补了 stainless 头后 REQ-06 是否还能有 40 分）。实际分数大概率在 45-60 之间，处于灰色地带。

### 2.2 蓝队的主动探测策略是否切实可行？

**PROBE-01（tool_use 探针）：可行且极具威胁，但有反制空间。**

优势：
- 利用了反代架构的根本缺陷（下游客户端无法执行 Claude Code 的文件系统操作）
- 85-95% 的检出率几乎是"必杀技"
- 误报率极低（真实 CLI 总是能处理 tool_use）

红队反制空间：
- 红队可以在反代层面实现 tool_use 拦截器：检测到 `get_workspace_info` 等探针工具时，生成虚假的 tool_result 回传。但工具名称会轮换，红队需要识别哪些是探针哪些是正常工具。
- 更关键的是，红队可以实现一个通用的 tool_result 生成器：对任何 tool_use 请求，基于工具名称和输入参数生成合理的模拟结果。这需要使用 LLM 生成合理的文件内容和命令输出，工程量大但理论可行。
- 但这会引入新的检测信号：如果蓝队分析 tool_result 的内容质量（如返回的文件路径是否真实存在于项目中、文件内容是否与之前的对话上下文一致），红队的虚假 result 可能暴露。

**判定：PROBE-01 是第二轮最强的新增检测手段。红队有理论上的反制路径，但工程难度极高。**

**PROBE-02（零宽字符水印）：脆弱，不构成实质威胁。**

红队一行代码可破解（strip 零宽字符）。虽然蓝队认为"移除零宽字符本身可成为检测信号"，但这个检测信号太弱（正常文本处理也会移除这些字符），不足以独立构成高置信度规则。

**PROBE-03（蜜罐账户）：可行但属于运营手段而非技术手段。**

蜜罐的价值不在于直接检出（检出范围仅限于使用了蜜罐凭证的流量），而在于收集反代指纹用于 ML 训练。这解决了蓝队的冷启动问题，是一个好的策略。但它属于情报收集而非实时检测，效果取决于蜜罐的传播效率。

### 2.3 BEH-05（请求内容画像）红队是否真的无法对抗？

**蓝队声称这是"红队几乎无法对抗的维度"。这个判断大体正确，但有条件。**

不可对抗的场景：
- SillyTavern 用户发送的角色扮演内容（`*action*` 格式、`{{char}}`/`{{user}}` 模板变量、NSFW 标记）与 Claude Code 的代码场景截然不同。BEH-05 的 RP_INDICATORS 可以精确捕获这些特征。
- 多轮对话无 tool_use/tool_result 是极强的信号。真实 Claude Code 的对话中 assistant 回复通常包含工具调用，这在反代的角色扮演场景中完全不存在。

可以对抗的场景：
- 如果下游用户本身就在做代码相关的工作（如使用反代访问 Claude 进行编程），BEH-05 完全无效。
- 红队可以在 system prompt 中注入代码上下文（项目目录结构、文件列表等），提高"代码味"指标。虽然红队自己承认这有风险，但对于 `code_ratio < 0.1` 的检测阈值，少量注入即可突破。
- 红队可以实现 tool_use 模拟器（如上文 PROBE-01 反制中讨论的），在对话中注入虚假的 tool_use/tool_result 交互。

**判定：BEH-05 对 SillyTavern 等纯角色扮演下游极为有效（检出率 80%+），但对代码场景下游无效。红队有一定的反制空间，但反制成本高且有副作用。总体上蓝队在此维度占优。**

### 2.4 多账户关联图分析（GRAPH-01）的可行性和工程成本

**可行性评估：理论可行，工程成本极高，投产比存疑。**

技术挑战：
1. **数据规模**：model-family API 的请求量可能达到每秒数千次。每个请求需要更新图的多条边，实时维护的写入压力巨大。
2. **社区发现算法的计算成本**：Louvain 算法在大图上的时间复杂度为 O(n log n)，但在数百万节点的实时图上定期运行仍然昂贵。
3. **存储**：IP x Cookie x Token x ClientID x Org 的关系图可能膨胀到数亿条边。需要专门的图数据库（如 Neo4j、TigerGraph）。
4. **时间窗口**：图需要某种时间衰减机制，否则历史数据会导致误关联。

实际效果：
- 对多 cookie 共享的反代集群有效（如同一个 clewdr 实例使用 10 个 cookie）。
- 但红队的 Cookie-IP 绑定 + 单 cookie 模式可以有效瓦解：每个实例只用 1 个 cookie、1 个 IP、1 个 client_id，图分析无法发现关联。
- 主要价值在于发现**未做好隔离**的反代集群，对精心配置的反代效果有限。

**判定：GRAPH-01 是一个好的理论方向，但工程投入与检出收益不成比例。建议蓝队将其作为第三轮的长期目标，而非第二轮的核心防线。**

### 3.3 仍在胶着的维度

| 维度 | 攻防现状 | 谁略占优 |
|------|---------|---------|

| NET-03 IP 行为 | 红队住宅代理 vs 蓝队云 IP 检测 | 取决于红队的运营预算 |

## 四、第三轮指引

### 4.1 红队第三轮应重点攻破

1. **PROBE-01 工具调用探针（最高优先级）**：这是蓝队第二轮最具威胁的新武器。红队需要实现 tool_use 拦截和模拟回传机制。具体方向：
   - 在反代层检测 assistant 回复中的 tool_use block
   - 对已知的 Claude Code 内置工具（Read, Write, Edit, Bash, Glob, Grep）生成合理的模拟结果
   - 关键挑战：tool_result 的内容需要与对话上下文保持逻辑一致性。可以考虑使用一个轻量级 LLM 来生成合理的假结果，或者在反代服务器上维护一个虚拟文件系统。

2. **BEH-05 内容画像（需要战略性应对）**：
   - 短期：在 system prompt 中注入 Claude Code 风格的工作区上下文（目录结构、文件列表、git 信息），提高 code_ratio
   - 中期：在下游请求中注入虚假的 tool_use/tool_result 历史消息，制造"工具使用"的假象
   - 长期：考虑分流策略 -- 代码类下游走 Claude Code 通道，非代码类下游走其他通道（如普通 API Key）

3. **NET-05 HTTP/2 指纹（必须覆盖）**：
   - 调研 hyper h2 crate 的 `Builder` 是否支持自定义 SETTINGS 参数
   - 抓取真实 Bun 的 HTTP/2 SETTINGS 帧参数值
   - 如果 hyper 不支持自定义，考虑 fork h2 crate 或使用 BoringSSL 方案

4. **BEH-03v2 body hash 比对的精确应对**：
   - count_tokens 的请求体必须使用与后续 chat 完全一致的 messages/system/model 字段
   - 实现起来不复杂（在 chat 前复制请求体发一次 count_tokens），但需要确保时序在 0.5-5 秒范围内

### 4.2 蓝队第三轮应重点防御

1. **加固 PROBE-01 的抗模拟能力**：
   - 探针工具名称定期轮换（不要固定为 `get_workspace_info`）
   - 校验 tool_result 的深层语义：如 `Read` 工具返回的文件内容是否与对话中提到的代码一致，`Bash` 返回的命令输出是否符合实际运行结果
   - 设计需要跨轮交互才能验证的探针序列（如先 Read 一个文件，然后在后续消息中引用文件内容）

2. **SSE 中继检测 (NET-06) 需要重新设计**：
   - 放弃基于 client_receive_timestamp 的检测方案（不可行）
   - 转向可行的替代方案：分析 TCP 层的 ACK 时序、窗口更新模式，或在 SSE event 中嵌入时序挑战（如随机延迟某个 event 并观察客户端是否注意到）

3. **内容画像 (BEH-05) 的鲁棒性增强**：
   - 不要只依赖静态正则匹配，加入 ML 文本分类器
   - 增加对"假注入"的检测：如果 system prompt 中包含代码上下文，但 user 消息中完全不引用这些上下文，这本身就是异常信号
   - 检测 tool_use/tool_result 链的时序一致性：真实 CLI 的工具执行需要时间（文件读写、命令运行），如果 tool_result 在 tool_use 后不到 100ms 就出现，说明是预生成的假结果

4. **降低 GRAPH-01 的工程复杂度**：
   - 不要追求实时全局图分析
   - 改为离线批处理：每小时汇总一次实体关联数据，运行社区发现算法
   - 聚焦最有价值的关联维度：client_id -> token 数量（最容易实现，检出率也高）

### 4.3 双方应关注的新维度

1. **Token Usage 异常检测**：
   - 蓝队可以监控单个 token 的总 token 消费量。反代共享 token 导致消费量远超正常单用户水平。
   - 红队需要对此做流量控制，但这直接削弱了反代的核心价值。

2. **API 端点访问模式**：
   - 真实 Claude Code CLI 在一个会话中的 API 调用序列有特定模式（如启动时 GET organizations -> POST messages -> count_tokens -> POST messages -> ...）。反代的调用序列可能缺少某些步骤。
   - 蓝队可以建模正常的 API 调用状态机，检测异常的状态转移。

3. **响应处理行为**：
   - 真实 CLI 在收到包含 tool_use 的响应后，会执行工具并在一定时间内发送包含 tool_result 的后续请求。这个"响应-处理-后续请求"的时间模式（工具执行延迟）是可以建模的。
   - 反代要么不发送 tool_result（被 PROBE-01 捕获），要么发送过快的假 tool_result（被时序分析捕获）。

### 5.3 综合评价

蓝队继续保持优势（8.5 vs 8.0），但差距从 1.0 缩小到 0.5。双方都有显著进步，但进步的方向不同：

- **红队的进步是"工程补全型"**：系统性地修补了第一轮的所有盲区，给出了逐条规则的数学推导。红队从"知道问题在哪但不知道怎么修"进化到了"知道问题在哪且给出了具体修复方案"。
- **蓝队的进步是"范式升级型"**：从被动检测升级到主动探测（PROBE 体系），从单点检测升级到语义级校验（BEH-03v2 body hash），从请求级分析升级到内容级分析（BEH-05）。蓝队打开了新的对抗维度。

蓝队的核心优势在于：反代的三个根本性矛盾（多用户共享 token、下游内容与 Claude Code 领域不匹配、无法执行真实的工具操作）在架构层面无法被红队解决。红队只能通过增加运营成本（每 cookie 单用户、内容注入、工具模拟）来缓解，但每一次缓解都削弱了反代的经济价值。

红队的核心优势在于：蓝队的检测系统复杂度在持续膨胀（从 v1 的 16 条规则到 v2 的 22+ 条），维护成本指数增长（版本追踪、ML 训练、蜜罐运营、探针轮换）。而红队只需要针对性地修复被识别的特征，攻防成本不对称（防守方维护成本 > 攻击方修复成本）。

**第三轮的关键转折点将是 PROBE-01（工具调用探针）和 BEH-05（内容画像）。如果红队能有效反制这两个维度，双方将进入真正的均势；如果不能，蓝队将建立压倒性优势。**
