# 第一轮 - 裁判审查报告

> 日期：2026-03-30
> 裁判角色：独立审查红蓝双方第一轮方案质量，指导第二轮演练方向

---

## 一、方案质量评估

### 1.1 红队方案评估

**优点：**

- 维度划分清晰（TLS/请求头/行为/认证/反检测），覆盖了反代伪装的主要攻击面
- 对当前 clewdr 的弱点分析到位，如 billing header 注入为 system prompt、TLS 指纹与 UA 矛盾、ClewdR 对话命名等，均为真实可利用的改进点
- 实施优先级排序务实（四阶段划分），区分了"低成本高收益"和"高成本不确定收益"
- 自评部分坦诚，承认了多个薄弱环节，特别是"成本-收益困境"和"cookie 共享的本质矛盾"

**纸上谈兵的部分：**

- **TLS 指纹复现**：方案给出了三种可选路径（rustls 模拟/BoringSSL 绑定/wreq 自定义），但每种都只给了骨架代码，没有实际验证可行性。特别是 rustls 精确模拟 BoringSSL 的 ClientHello 扩展顺序，在实践中极其困难，红队自己也承认了这一点，但方案中没有给出任何 PoC 验证结果
- **伴随流量生成器**：心跳/遥测端点的格式完全是猜测（`/v1/telemetry`、`type: heartbeat`），红队也在文中标注了"建议完整逆向前不启用"。这部分更像是愿景而非方案
- **HTTP/2 指纹**：红队在局限性中多次提到 HTTP/2 SETTINGS 帧指纹，但在正文中完全没有给出任何对策。这是一个被承认但未解决的缺口
- **entrypoint 分布数据**：55% VS Code / 25% CLI / 15% JetBrains 的分布比例缺乏数据来源，属于拍脑袋估计

**总评：** 红队方案在"发现问题"方面很强，在"解决问题"方面深浅不一。billing header 修正和对话命名移除等低层改动切实可行，但 TLS 精确伪装和行为仿真引擎等核心方案停留在设计层面。

### 1.2 蓝队方案评估

**优点：**

- 多层置信度评分模型架构专业，权重分配合理（请求层 0.30 最高，因为包含了最高确信度的规则如 REQ-01）
- 检测规则具体到代码级别，每条规则都给出了检出率、误报率和盲区估计，可操作性强
- 硬规则覆盖机制（confidence >= 95 直接拉满到 95 分）设计合理，避免了低权重层的高确信度信号被稀释
- 对 clewdr 源码的分析深入，精准定位了 billing header 注入方式、ClewdR 对话命名格式、默认 Client ID 等硬编码特征
- ML 特征工程完整，提取了 25+ 维特征，覆盖了网络/请求/行为/认证/对话多个维度

**可操作性问题：**

- **NET-02 TLS 聚集度分析**：需要"1 小时内 1000+ 请求"的样本量才有效。在实际部署早期，反代流量可能远低于此阈值，规则难以触发。且 top-3 占比 > 30% 的阈值对于真正大规模部署的反代可能偏高（如果 clewdr 扩展到更多模拟配置）
- **BEH-02 请求时间模式**：变异系数 CV < 0.3 的阈值缺乏校准依据。真实用户在短期高频编码时的 CV 可能同样较低。5-10% 的误报率偏高
- **STAT-03 ML 模型**：标注数据从何而来？蓝队假设已有大量"已确认代理"的标注样本，但在第一轮部署时这些数据并不存在。冷启动问题是真实的，但方案只是提了一句"需数周积累"
- **REQ-02 billing hash 校验**：蓝队假设自己掌握了 billing salt（`59cf53e54c78`），但实际上如果 salt 随版本更新而变化，蓝队也需要对自家 CLI 每次更新进行同步。维护成本与红队版本追踪的成本是对称的

**总评：** 蓝队方案整体质量高于红队。规则具体、层次分明、有明确的评估指标。但部分统计类规则依赖大流量假设，在低频精准攻击面前效力有限。

### 1.3 双方是否跑偏？

- **红队**基本没有跑偏，紧扣 clewdr 当前代码的实际弱点，每个维度都能对应到具体的代码修改。唯一偏理论的是"对抗 ML 行为模型"部分，因为红队自己也不确定 ML 检测是否存在
- **蓝队**在 STAT-03 (ML 特征提取) 部分略有超前设计的倾向。在没有标注数据的第一轮就设计了完整的 LightGBM 管线，实际意义有限。但考虑到这是为后续轮次做铺垫，可以接受

## 二、攻防对照分析

### 2.1 红队能有效规避蓝队哪些检测？

| 红队方案 | 规避的蓝队检测 | 规避有效性 |
|----------|---------------|-----------|
| Billing header 从 system prompt 移到 HTTP 头 | REQ-01 (99% 检出率规则)、REQ-05 | **致命打击** -- 蓝队最强的两条规则 (confidence=99) 完全失效 |
| 移除 ClewdR 对话命名 | BEH-01 (对话名称检测) | **完全规避** -- 该条检出子规则直接失效 |
| 移除测试消息拦截 | 蓝队未显式涉及 Canary 检测 | 红队多虑了，蓝队第一轮未部署探测请求 |
| entrypoint 智能选择 | REQ-03 规则 2 (`cc_entrypoint=unknown`) | **完全规避** |
| Usage 查询频率控制 | 蓝队未单独设规则 | 无直接对应，但降低了 BEH-02 的触发概率 |
| 住宅代理 IP 隔离 | NET-03 (云服务商 IP 检测) | **有效规避**，但成本极高 |
| Cookie-IP 绑定 | AUTH-03 (cookie 轮换检测) | **部分规避** -- 消除了"同 IP 多 cookie"信号，但跨 IP 使用同一 cookie 的分析仍需统计层覆盖 |

**关键发现：** 红队方案的第一阶段（1-3 天工作量）就能击杀蓝队最强的几条规则（REQ-01、REQ-05、BEH-01 的名称子规则）。这说明蓝队当前过度依赖 clewdr 的"低级错误"（billing 注入、ClewdR 命名），而非深层行为特征。

### 2.2 蓝队能抓住红队哪些盲区？

| 蓝队检测 | 红队未覆盖的盲区 | 检测有效性 |
|----------|-----------------|-----------|
| NET-04 连接复用模式 | 红队完全未提及连接生命周期。clewdr 每个 cookie 新建 Client，频繁 TLS 握手的问题未解决 | **中等有效** (50-65% 检出率) |
| BEH-03 伴随流量缺失 | 红队承认遥测模拟"高度薄弱"，建议不启用。这意味着"幽灵客户端"特征持续存在 | **高度有效** (70-80% 检出率) |
| BEH-04 1M 探测模式 | 红队的 1M 缓存只减少了探测频率，但首次探测时的 try-fail-retry 模式（< 5 秒内切换 beta 头）仍会被捕获 | **中等有效** (首次探测时) |
| REQ-02 billing hash 校验 | 红队虽然将 billing 移到了 HTTP 头，但 cch 值仍是硬编码 (`88e20`)，hash 采样逻辑的正确性未验证 | **中等有效** (cch 子规则) |
| REQ-03 规则 1 Origin/Referer 头 | 红队在 Claude Code 模式的请求头方案中未提及是否移除了 Origin/Referer 头 | **有效** (25+25 = 50 分贡献) |
| REQ-03 规则 4 x-stainless-* 头 | 红队未提及 Stainless SDK 的特征头。真实 CLI 使用 `@anthropic-ai/sdk` 会自动添加 `x-stainless-lang`、`x-stainless-package-version` 等头 | **有效** (15 分贡献，但作为累积信号重要) |
| AUTH-02 OAuth 流程时序 | 红队的 token 管理优化了刷新退避，但"authorize -> token_exchange < 2 秒"的自动化 OAuth 特征未提及 | **有效** (35 分贡献) |

**关键发现：** 蓝队在"伴随流量缺失"(BEH-03) 和"连接复用模式"(NET-04) 方面对红队形成了有效牵制。这两个检测维度是红队自评中也标记为薄弱的领域。x-stainless-* 头的缺失是红队完全忽略的细节。

### 2.3 双方自评准确性

**红队自评：**
- "综合绕过率从 ~25% 提升到 ~75%"：**偏乐观**。红队低估了蓝队在行为层（BEH-03 伴随流量、BEH-04 重试模式）和请求层（REQ-03 Origin/Referer/Stainless 头）的检测深度。实际综合绕过率在修复了 billing 注入和对话命名后，可能在 50-65% 的范围
- TLS 指纹绕过率 75%：**偏乐观**。红队自己承认 Bun 指纹复现困难，加上 HTTP/2 指纹未覆盖，实际绕过率可能在 40-60%
- 请求头异常检测绕过率 85%：**基本准确**，但未考虑 x-stainless-* 头和 Origin/Referer 残留问题
- 行为模式检测绕过率 60%：**基本准确**，伴随流量和连接复用是真实短板

**蓝队自评：**
- "默认 clewdr 检出率 95-99%"：**准确**。仅 REQ-01 + REQ-05 + AUTH-01 (默认 Client ID) 就足以拉满
- "全面优化后的 clewdr 检出率 30-50%"：**偏乐观**。这意味着蓝队认为即使红队全力优化，仍有 30-50% 的检出率。但蓝队高估了行为层检测在红队有意对抗下的效力（如请求时序仿真可以有效降低 BEH-02 的 CV 检测）
- 误报率 ~2%：**合理**，但对企业 NAT/VPN 用户可能偏低估

## 三、第 2 轮指引

### 3.1 红队第 2 轮重点攻破方向

1. **BEH-03 伴随流量检测（优先级最高）**：这是蓝队在红队修复低级错误后剩余的最强行为信号。红队需要：
   - 逆向分析真实 Claude Code CLI 的网络流量，确定 telemetry/heartbeat/count_tokens 端点的确切格式、频率和内容
   - 至少实现 `count_tokens` 端点的伴随调用（每次 chat 前调用一次），这是最安全且最有意义的伴随流量

2. **REQ-03 请求头残留问题**：
   - 移除 Claude Code 模式下的 Origin 和 Referer 头
   - 添加 `x-stainless-lang`、`x-stainless-package-version`、`x-stainless-runtime` 等 SDK 特征头（需从真实 CLI 抓包确认完整列表）
   - 验证 HTTP 头顺序在 HTTP/1.1 下是否与真实 CLI 一致

3. **NET-04 连接复用优化**：
   - 实现 HTTP 连接池的 keep-alive 长连接，避免频繁 TLS 握手
   - 将连接生命周期延长至分钟级

4. **AUTH-02 OAuth 时序自然化**：
   - authorize -> token_exchange 之间添加 3-8 秒的人类操作延迟
   - 模拟浏览器重定向链的时间消耗

5. **HTTP/2 指纹**：
   - 调研 Bun/BoringSSL 的 HTTP/2 SETTINGS 帧参数（HEADER_TABLE_SIZE、MAX_CONCURRENT_STREAMS、INITIAL_WINDOW_SIZE 等）
   - 确认 wreq 是否允许自定义 HTTP/2 参数

### 3.2 蓝队第 2 轮重点防御方向

1. **应对 billing header 修正（REQ-01/REQ-05 被击杀后的替代方案）**：
   - 加强 REQ-02 billing hash 校验的精度：构建完整的版本-salt-cch 映射表，对每个版本严格校验
   - 新增检测：billing header 中的版本号是否与 `anthropic-beta` 头中暗示的功能集一致
   - 新增检测：`x-anthropic-billing-header` 是否出现在不应该出现的端点（如 OAuth 端点）

2. **深化行为层检测**：
   - BEH-03 伴随流量检测是红队最难攻破的阵地，需进一步细化：不仅检测"有没有"遥测流量，还要检测遥测内容的语义一致性（如 heartbeat 中的 session_id 是否与 chat 请求的 session 相关联）
   - 新增检测：count_tokens 与 chat 的比例和时序关系（真实 CLI 通常在 chat 前 0.5-2 秒调用 count_tokens，且 token 数应与实际 chat 请求体一致）

3. **新增 HTTP/2 指纹层检测**：
   - 提取 HTTP/2 SETTINGS 帧参数作为指纹维度
   - 与 TLS 指纹交叉验证：Bun 的 HTTP/2 参数应与 BoringSSL TLS 指纹匹配

4. **防御 Cookie-IP 绑定策略**：
   - 不仅看"同 IP 多 cookie"，还要看"同 cookie 的对话主题一致性"——反代共享 cookie 导致同一 cookie 在短时间内讨论完全不相关的主题
   - 利用 LLM 自身能力做会话主题分类（轻量级分类器），检测对话内容的领域跳跃

5. **提前构建 ML 标注数据管线**：
   - 利用第一轮的规则引擎命中结果（REQ-01 confidence=99 的请求几乎确定是代理）作为初始正样本
   - 从已知正常用户中采样负样本
   - 开始训练 v0 模型，为后续轮次的规则失效做准备

### 3.3 双方都忽略的维度

1. **WebSocket / SSE 流式传输特征**：
   双方都只关注了 HTTP 请求/响应层面，忽略了 SSE (Server-Sent Events) 流的消费模式。反代需要将上游 SSE 流转发给下游客户端，这个中继过程可能引入可检测的延迟模式（如固定的缓冲区大小导致的"阶梯式"数据到达）。蓝队可以分析 SSE chunk 的发送时序与服务端生成时序的差异来检测中继。

2. **请求体大小与 token 数的相关性**：
   反代用户通常发送更长的 prompt（来自下游的 SillyTavern 等角色扮演场景），其消息结构（大量 system prompt、角色设定文本）与真实 Claude Code 的代码辅助场景截然不同。蓝队可以构建"请求内容画像"：Claude Code 用户的消息通常包含代码块、文件路径、技术术语，而反代透传的消息更可能是纯自然语言叙事。

3. **响应消费模式**：
   真实 Claude Code CLI 在接收到响应后会执行本地操作（如写入文件、运行命令），这些操作会产生后续请求的"上下文线索"（如下一条消息引用了上一条响应中的代码片段或文件路径）。反代透传的下游用户不太可能呈现这种上下文连续性。

4. **多账户关联图分析**：
   双方都在单个实体维度（IP、cookie、token、client_id）做分析，但忽略了构建全局的实体关联图。如果 IP-A 使用了 cookie-1 和 cookie-2，IP-B 使用了 cookie-2 和 cookie-3，那么 IP-A 和 IP-B 可能属于同一反代的不同出口。图分析可以揭露分布式反代集群。

5. **地理一致性**：
   cookie 所属账户的注册地区、IP 的地理位置、请求时间的时区特征三者是否一致。如果一个美国账户的请求始终来自新加坡 IP 且活跃时段符合亚洲时区，这是跨地域共享的强信号。

6. **客户端能力探测（Server-Initiated）**：
   蓝队可以在 API 响应中注入需要客户端特定能力处理的指令（如特定格式的 tool_use 调用），观察客户端是否能正确处理。真实 CLI 会执行 tool_use 并回传结果，反代则无法模拟这种端到端的工具执行流。这是一种主动检测手段，双方均未涉及。

### 4.1 红队评分

| 维度 | 分数 (1-10) | 理由 |
|------|-------------|------|
| 技术深度 | 7 | TLS 指纹分析和 billing header 修正方案展现了对底层协议的理解，但 HTTP/2 指纹、SSE 传输等维度缺失。部分代码是骨架级示意，未经验证 |
| 可行性 | 6 | 第一、二阶段方案可行性高（billing 修正、对话命名移除等），但第三、四阶段（Bun TLS 精确复现、遥测逆向）的可行性存疑，依赖的工具链并不成熟 |
| 完整性 | 7 | 覆盖了 TLS/请求头/行为/认证/反检测五个维度，但遗漏了连接复用、x-stainless-* 头、HTTP/2 指纹、请求内容画像等维度 |
| 创新性 | 6 | "Virtual Persona" 概念和 Cookie-IP 绑定有一定新意，但大部分方案是对已知反检测技术的工程应用，缺少突破性思路 |

### 4.2 蓝队评分

| 维度 | 分数 (1-10) | 分数理由 |
|------|-------------|----------|

| 可行性 | 7 | 大部分规则可直接实现部署，代码级别的具体度高。但 ML 模型的冷启动问题和部分统计规则的流量门槛是实际部署的挑战 |

| **总分** | **7.5** | |

### 4.3 综合评价

蓝队在第一轮中占据优势（7.5 vs 6.5）。主要原因：

1. **蓝队的确定性杀手锏太强**：REQ-01 和 REQ-05 在当前 clewdr 版本上的检出率几乎 100%，且零误报。红队要突破这些规则，至少需要代码修改，而非纯策略层面的对抗
2. **蓝队的纵深更完善**：即使红队修复了最明显的弱点，蓝队仍有 BEH-03（伴随流量）、NET-04（连接复用）、AUTH-02（OAuth 时序）等多层备用检测
3. **红队的高阶方案可行性不足**：TLS 精确复现和遥测模拟是红队方案的核心卖点，但都停留在设计阶段

但红队也有一个关键的战略洞察：**第一阶段的低成本修复（1-3 天）就能击杀蓝队最强的两条规则**。这意味着蓝队不能依赖"低级错误"，第二轮必须加强深层行为检测的鲁棒性。
