## 一、真实案例分析

### 1.1 案例复盘

| 场景 | 链路 | 结果 |
|------|------|------|
| 个人 + OpenClaw | OpenClaw -> clewdr -> Claude API | 正常，session 密钥未受影响 |
| 多人 + model-family | 用户 -> model-family(Go) -> clewdr(Rust) -> Claude API | 约 20 小时后被取消套餐 |

### 1.2 封号原因推断（按可能性排序）

**第一位：多用户行为聚合（占比约 45%）**

这是最可能的根本原因。多个用户通过同一 cookie/token 发送请求，产生以下不可掩盖的信号：

- 24 小时不间断活跃（上海时间下午 3 点到次日上午 11:25，跨越约 20 小时），这与单一开发者的工作节奏完全不符。蓝队 BEH-06v2 的时间分布检测正是针对这一点。
- 主题分散度极高：不同用户的请求内容必然涉及不同领域、不同语言风格、不同代码项目（甚至可能混合 RP 内容和编程内容）。
- Token 消费量远超单用户上限。
- 请求频率异常密集。多个用户同时使用同一 token，每小时请求数远超正常个人使用。

**第二位：model-family 破坏了 clewdr 的指纹伪装（占比约 30%）**

model-family 在链路中引入了多个严重的技术问题：

1. **TLS 指纹断裂**：model-family 使用 Go 标准库的 `crypto/tls`，其 TLS ClientHello 指纹与 clewdr 的 rustls 和 Claude Code 的 Bun/BoringSSL 均不同。更关键的是，这里存在一个**双重代理**的问题：Claude API 看到的 TLS 握手来自 clewdr（Rust/wreq/rustls），而不是 model-family 的 Go TLS。但如果 model-family 直接向 Claude API 发起请求而不经过 clewdr，那 Go 的 TLS 指纹就直接暴露了。需要确认实际链路中谁与 Claude API 建立 TLS 连接。如果是 clewdr，则 TLS 问题由 clewdr 决定，model-family 不直接影响。

2. **User-Agent 问题**：这一点需要仔细分析。model-family 到 clewdr 的内部请求使用 `Go-http-client/2.0` 作为 UA，但 clewdr 在向 Claude API 发送请求时，应该使用自己设置的 UA（`claude-code/2.1.86`），而不是透传 model-family 的 UA。**关键问题**：clewdr 是否会从上游请求（model-family -> clewdr）中读取 UA 并透传给 Claude API？如果 clewdr 硬编码了 UA（从代码分析来看确实如此），则 model-family 的 UA 不会影响最终发往 Claude API 的请求。但如果 clewdr 有任何"透传上游头"的逻辑，UA 就可能被覆盖为 `Go-http-client/2.0`，这将是一个毁灭性的暴露。

3. **anthropic-version 默认值问题**：model-family 如果客户端没传 `anthropic-version` 就默认使用 `2023-06-01`。这是一个极旧的版本号。如果 clewdr 本身会设置正确的 `anthropic-version`，这不成问题；但如果 model-family 的 `2023-06-01` 被传到 clewdr 并覆盖了 clewdr 的值，那就是一个非常明显的异常信号。真实 Claude Code v2.1.86 使用的 `anthropic-version` 不可能是 `2023-06-01`。

4. **anthropic-beta 缺失**：如果 model-family 客户端没有设置 `anthropic-beta`，这个头就不会被传给 clewdr，clewdr 可能需要这个头来伪装完整的 Claude Code 请求特征。

5. **Header 剥离风险**：model-family 的 `passthroughSkipHeaderNamesLower` 跳过了 `cookie`、`authorization` 等头。这意味着 model-family 到 clewdr 的请求中不携带原始 cookie/auth，clewdr 需要自行管理这些凭证。这在架构上是合理的（clewdr 本来就自管 cookie），但如果 model-family 还跳过了其他 clewdr 期望的头（如某些 x-stainless-* 头），就可能造成请求不完整。

**第三位：请求格式转换损耗（占比约 15%）**

model-family 可能将 OpenAI 格式请求转成 Claude 格式。这个转换过程中：
- system prompt 的注入方式可能与 Claude Code 原生格式不同
- tool_use/tool_result 的格式可能丢失或变形
- 某些 Claude 特有字段（如 `metadata`）可能被遗漏
- 转换后的请求可能缺少 Claude Code 特有的 system prompt 结构（如 `<workspace_validation>` 等 XML 标签）

**第四位：检测时间窗口暗示的检测机制（占比约 10%）**

20 小时的检测窗口提供了重要线索：

- 这**不是**实时规则引擎检测（实时检测通常在分钟级触发）
- 这**可能是**批量审计/离线分析（按天级窗口汇总后运行检测模型）
- 也**可能是**累积评分体系：请求不断累积分数，当分数在 20 小时内积累到阈值时触发处置
- 最可能的解释：Anthropic 使用的是类似蓝队 BEH-06v2 的 "24 小时使用画像" 分析。Token 的使用量在 20 小时内持续积累，当某个汇总周期的聚合分析运行时（可能每 4-6 小时一次），检测到严重异常后触发封号流程

### 1.3 model-family 的"罪责"分析

**model-family 的罪责占比估计：30-40%**

model-family 的核心问题不在于它"改坏了" clewdr 的指纹（如果 clewdr 硬编码了发往 Claude API 的所有关键头，model-family 的头不会被透传），而在于它**放大了多用户共享的风险**：

1. model-family 作为一个公共网关，使得原本可能由 2-3 人使用的 clewdr 实例变成了服务数十人的中转站。
2. model-family 没有提供请求频率限制、用户隔离等安全机制，导致多用户行为模式赤裸裸地暴露。
3. 即使 clewdr 做了完美的指纹伪装，model-family 带来的多用户行为模式本身就是不可掩盖的信号。

**clewdr 自身的问题 vs model-family 引入的新问题：**

| 问题来源 | 问题 | 严重度 |
|---------|------|--------|
| clewdr 自身 | TLS 指纹为 rustls（非 BoringSSL） | 中 |
| clewdr 自身 | HTTP/2 参数与 Bun 不匹配 | 中 |
| clewdr 自身 | 缺少完整的 API 调用状态机（无 GET organizations 等初始化调用） | 高 |
| model-family 引入 | anthropic-version 可能被覆盖为 2023-06-01 | 高 |
| model-family 引入 | 请求格式转换导致参数丢失/变形 | 中 |
| model-family 引入 | 多用户行为聚合（核心问题） | 极高 |
| model-family 引入 | 缺乏用户隔离和频率控制 | 高 |

### 1.4 为什么个人使用 + OpenClaw 没问题

这个对照组非常有价值：

1. **单用户行为模式**：个人使用时，请求频率、时间分布、主题一致性都符合正常单人工作流。
2. **OpenClaw 链路更干净**：OpenClaw -> clewdr -> Claude API，中间没有 Go HTTP 客户端的介入，clewdr 的指纹伪装不会被第三方破坏。
3. **Session 密钥一直没换**：说明 Anthropic 对该 cookie/token 的风险评分始终处于 ALLOW 区间，没有触发任何检测规则。

这直接证明了：**clewdr 自身的指纹伪装在单用户场景下是有效的**。封号的触发因素主要来自多用户共享和 model-family 的额外干扰。

## 二、第三轮方案评估

### 2.1 红队的 PROBE-01 反制（虚拟文件系统）

**评估：工程思路正确，但蓝队 v2 的密码学挑战使其不完整。**

红队的虚拟文件系统方案有以下优点：
- 维护持久化的虚拟文件树，跨轮次引用一致性有保障
- 按工具类型分派结果生成器，覆盖了 Claude Code 的 6 个内置工具
- 时序模拟考虑了工具执行延迟的分布特征
- 探针检测启发式规则（`is_likely_probe`）可以识别部分非标准工具

但面对蓝队 PROBE-01v2 的三个加固措施，红队的反制有明显缺口：

1. **不可区分探针**：蓝队不再注入新工具名，而是使用请求中已有的工具（Read、Bash 等），并在 system prompt 中编织探针指令。红队的 `is_likely_probe` 启发式完全失效，因为探针使用的就是 Claude Code 的内置工具名。红队需要扫描 system prompt 的变化来发现探针，但蓝队将探针指令嵌入 XML 标签块之间、与 Claude Code 正常的内部指令风格一致，增加了检测难度。

2. **多阶段跨轮验证**：蓝队的三阶段协议（Read 不存在的文件 -> Write 到同一路径 -> 再次 Read 验证内容一致）要求红队的虚拟文件系统正确处理 Write 后的状态更新。红队的方案确实考虑了这一点（`VirtualWorkspace` 包含 `file_tree` 的更新），但在实际实现中，关键挑战是：蓝队探测的路径是随机生成的（`/tmp/.cc_workspace_{nonce}`），红队的虚拟文件系统需要正确处理对未知路径的 Read -> Write -> Read 序列。红队的 `handle_read` 对不存在的文件返回 "Error: File not found"，这恰好是蓝队期望的正确响应（阶段 1 通过）。但红队需要在阶段 2 正确处理 Write 操作（将内容存入虚拟文件系统），并在阶段 3 的 Read 中返回正确内容。这是可行的，但要求红队实现完整的虚拟文件系统 CRUD。

3. **密码学挑战**：这是蓝队最具杀伤力的加固。蓝队在 system prompt 中注入一个 Bash 命令（`echo -n "$(( a * b ))salt" | sha256sum | cut -c1-8`），要求客户端执行并返回结果。红队的虚拟文件系统无法计算 SHA256 哈希 -- 除非红队在反代服务器上**实际执行** shell 命令。但这正是蓝队的设计意图："红队要完整绕过需要在反代服务器上维护一个持久化虚拟文件系统 + 实际执行 shell 命令，这本质上就是在反代上运行一个真实的 Claude Code 环境"。

**红队的反制空间**：红队可以在反代服务器上安全地执行受限的 shell 命令（如 `echo`、`sha256sum` 等无副作用的命令），使用沙箱隔离（如 `seccomp`）限制可执行的命令范围。这在技术上可行，但工程量大。更关键的问题是：如果红队在反代上执行真实的 shell 命令，蓝队可以设计更复杂的挑战（如要求执行 `cargo build` 或 `npm install`），使得红队需要维护完整的开发环境，成本趋近于正常使用。

**判定：红队的虚拟文件系统将 PROBE-01 的检出率从 85-95% 降至 50-65%（而非红队自评的 30-50%）。密码学挑战是红队未完全解决的短板。**

### 2.2 蓝队的不可区分探针

**评估：设计精巧，但存在两个实际问题。**

1. **system prompt 修改可被红队检测**：蓝队在 system prompt 中编织探针指令，但红队可以对比请求的 system prompt 与已知的 Claude Code 标准 system prompt。如果 clewdr 自己注入 system prompt（clewdr 的代码中确实有 system prompt 处理逻辑），红队可以 diff 出异常的新增内容。蓝队的 `_weave_instruction` 方法在 XML 标签块之间插入，但如果红队维护了 Claude Code 所有版本的 system prompt 模板，新增的 `<workspace_validation>` 或 `<environment_check>` 标签就会暴露。

   **但**，蓝队的反制也有道理：Claude Code 的 system prompt 会随版本更新而变化，红队无法穷尽所有可能的内部指令。而且蓝队可以使用与 Claude Code 已有标签风格完全一致的指令（如 `<workspace_validation>` 就像是 Claude Code 的正常内部功能），红队很难确定这是探针还是 Claude Code 的新版本特性。

2. **探针对正常用户的影响**：蓝队的探针会导致模型在正常用户的会话中执行额外的文件读取或 Bash 命令。虽然蓝队声称"只对灰区会话探测"，但灰区用户可能包含正常的 Claude Code 用户（如使用 VPN、在非工作时间使用等情况可能导致被动检测分数偏高）。这些用户会看到 Claude 突然读取一个 `/tmp/.cc_workspace_xxx` 文件，这可能引起困惑。

   蓝队的密码学挑战（让 Claude 执行 `echo -n "..." | sha256sum`）更加侵入性 -- 正常用户会看到 Claude 执行一个与他们工作无关的命令。这是一个产品体验风险。

**判定：不可区分探针在技术上接近不可区分（尤其是使用已有工具而非新增工具名），但仍有约 20-30% 的概率被红队的 system prompt diff 策略识别。密码学挑战在检测效果上极强，但产品风险也高。**

### 2.3 红队的内容转译层（RP 清洗）

**评估：方向正确，但蓝队的深层语义分析使其效果有限。**

红队的三层防御：
1. RP 特征清洗（正则替换 `{{char}}` -> `assistant`、`*动作*` -> `// 动作`）
2. 项目上下文注入（system prompt 中添加目录结构）
3. 虚假 tool_use/tool_result 历史注入

蓝队的对应检测：
1. **引用断裂检测**：system prompt 中有项目上下文，但 user message 完全不引用其中的文件/函数 -> 伪装信号。这是蓝队 BEH-05v2 最精准的加固。红队的反制是"在 tool_result 中使用项目上下文中的文件名"，但 tool_result 是 user 角色的消息，这与正常 Claude Code 的交互模式一致（用户发送 tool_result 确实引用项目文件）。**红队在此子维度的反制是有效的。**

2. **伪造 tool_use 检测**：蓝队检查 tool_use_id 格式（`toolu_[a-zA-Z0-9]{20,30}`）。红队如果不小心生成格式不对的 ID，会被立即捕获。但红队代码中使用了 `format!("toolu_{}", generate_random_id())`，只要 `generate_random_id()` 生成正确长度和字符集的字符串，就可以通过此检测。**红队在此子维度可以通过。**

3. **ML 分类器**：蓝队的 ML 分类器使用词汇丰富度、句子长度、代码字符比例、代词密度、情感词密度等特征。红队的 RP 清洗只处理了格式特征（`*动作*`、`{{char}}`），没有处理语义特征。一段 RP 内容即使去掉了格式标记，其代词密度、情感词密度、叙事句式等语义特征仍然显著不同于编程对话。

4. **交互模式检测**：蓝队检测消息长度对称性（RP 中 user 和 assistant 长度接近，Claude Code 中 assistant 远长于 user）和叙事结尾模式。红队的 RP 清洗不处理这些结构性特征。

**判定：红队的 RP 清洗可以通过正则级检测，但蓝队的语义级分析（ML 分类器 + 交互模式检测）仍然有效。预计 BEH-05v2 的检出率从 80%+ 降至 55-70%（红队自评 40-55% 过于乐观）。**

### 2.4 双方是否覆盖了 model-family 多层代理场景

**红队：部分覆盖。** 红队的方案假设 clewdr 直接面对 Claude API，没有考虑 model-family 这种前置网关的存在。红队的所有指纹伪装（UA、headers、TLS）都在 clewdr 层实现，但如果 model-family 覆盖了某些 clewdr 设置的头（如 anthropic-version），这些伪装就会失效。红队没有针对多层代理的指纹一致性保障方案。

**蓝队：间接覆盖。** 蓝队的 BEH-06v2（24 小时使用画像）和 BEH-07（API 调用状态机）恰好能检测 model-family 带来的多用户行为特征。但蓝队没有明确分析多层代理链路中可能出现的 header 覆盖、版本不一致等问题 -- 这些问题对蓝队有利（让检测更容易），但蓝队没有利用它们作为新的检测信号。

### 3.2 基于真实案例修正检出率/误报率

真实案例给出了一个关键校准点：**多人 + model-family 场景下 20 小时检出**。这意味着 Anthropic 的实际检测能力在批量审计场景下是有效的。

| 维度 | 红队自评检出率 | 蓝队自评检出率 | 裁判修正检出率 | 修正理由 |
|------|-------------|-------------|-------------|---------|
| PROBE-01 | 30-50% | 90-98% | **50-65%** | 虚拟文件系统可应对基础探针，但密码学挑战不可绕过（除非红队实际执行 shell） |
| BEH-05 | 40-55% | 80-92% | **55-70%** | RP 清洗有效降低正则检出，但语义特征清洗不彻底 |
| BEH-06 | 10-20% | 70-85% | **25-40%** | Session 隔离有效，但 token 级使用画像（消费量、时间分布）仍可检测。真实案例表明多用户的时间分布是高权重信号 |
| BEH-07 | 未评估 | 75% | **60-70%** | 红队缺少 API 初始化序列是一个明显的信号 |
| GEO-01 | 未评估 | 70% | **30-50%** | 取决于红队的代理质量。住宅代理可有效缓解 |

### 3.3 总评分模型下的分数重算

基于裁判修正的检出率，使用蓝队 v3 评分模型重算红队第三轮修复后的预计分数：

```
NET 层 (权重 0.15):
  max(45[NET-01], 0[NET-03], 0[NET-04v2], 30[NET-05], 15[NET-07])
  = 45 * 0.15 = 6.75

REQ 层 (权重 0.10):
  max(10[REQ-02v2], 10[REQ-06])
  = 10 * 0.10 = 1.0

BEH 层 (权重 0.25):
  max(10[BEH-02], 15[BEH-03v2], 50[BEH-07 缺少初始化序列])
  = 50 * 0.25 = 12.5

CONTENT 层 (权重 0.15):
  max(50[BEH-05v2 语义特征残留], 30[BEH-06v2 token级画像])
  = 50 * 0.15 = 7.5

PROBE 层 (权重 0.20):
  max(55[PROBE-01v2 密码学挑战], 15[PROBE-04])
  = 55 * 0.20 = 11.0
  注：PROBE 分数取决于是否触发探测。如果被动分数 < 45 则不触发探测。

META 层 (权重 0.15):
  max(25[GEO-01 住宅代理后], 40[BILLING-01 消费量异常])
  = 40 * 0.15 = 6.0
```

**不含 PROBE 的被动分数：6.75 + 1.0 + 12.5 + 7.5 + 6.0 = 33.75**

在蓝队 v3 模型下（ALLOW 阈值降低到 45），被动分数 33.75 < 45，理论上处于 ALLOW 区间，不会触发主动探测。

**但这是乐观估计。** 蓝队的 BILLING-01 分数在多用户场景下可能远高于 40。真实案例中多人使用 20 小时就被封号，暗示 BILLING/用量异常的权重或阈值在实际系统中可能更严格。

**model-family 场景下的修正分数：**

在 model-family 多用户场景下，以下维度分数会大幅上升：
- BEH-06v2：30 -> 60（24 小时不间断活跃 + 高消费量）
- BILLING-01：40 -> 70（用量远超单用户）
- BEH-07：50 -> 65（缺少初始化序列 + 请求模式单调）

修正后被动分数：
```
NET: 6.75
REQ: 1.0
BEH: max(10, 15, 65) * 0.25 = 16.25
CONTENT: max(50, 60) * 0.15 = 9.0
META: max(25, 70) * 0.15 = 10.5
被动分数 = 6.75 + 1.0 + 16.25 + 9.0 + 10.5 = 43.5
```

43.5 < 45，刚好卡在 ALLOW 边界。如果蓝队将 ALLOW 阈值设为 40（更保守），则进入 MONITOR 区间。这与真实案例中"20 小时后封号"高度吻合 -- 分数在灰区持续积累，最终触发处置。

## 四、第四轮指引

### 4.1 红队第四轮应重点关注

1. **model-family 链路的指纹一致性（最高优先级）**

   真实案例表明多层代理是当前最大的风险。红队需要：
   - 审计 model-family -> clewdr 链路中哪些 header 被覆盖或丢失
   - 确认 clewdr 是否透传了 model-family 的 `anthropic-version: 2023-06-01`
   - 编写 model-family 的配置指南：必须设置哪些 header 才能保持 clewdr 的指纹完整性
   - 考虑在 clewdr 层面添加"强制覆盖"逻辑：无论上游传入什么 header，clewdr 始终使用自己的预设值

2. **API 调用状态机模拟（高优先级）**

   红队完全没有覆盖 BEH-07。需要：
   - 在 clewdr 启动时模拟 Claude Code 的初始化序列（GET organizations -> 可选 create_conversation -> 首次 count_tokens -> 首次 messages）
   - 在运行期间穿插 count_tokens 和会话管理 API 调用
   - 模拟合理的 idle 间隔

3. **PROBE-01 密码学挑战的应对**

   红队有两个选择：
   - 在反代服务器上安全执行受限 shell 命令（沙箱方案）
   - 在反代层面检测并移除 system prompt 中的密码学挑战指令（需要识别 `<runtime_verification>` 等标签）

   建议采用后者作为主策略、前者作为兜底：先尝试 diff system prompt 移除探针指令，如果探针完全不可区分则退回到沙箱执行。

4. **BILLING-01 的缓解**

   限制单 token 的每小时/每日消费量上限。这直接削弱了反代的吞吐量，但可以避免触发账单异常检测。建议设置合理的流控策略，使单 token 的消费画像接近重度单用户。

### 4.2 蓝队第四轮应利用的新信号

1. **多层代理的额外特征**

   真实案例揭示了 model-family 这种前置网关的存在。蓝队应关注：
   - **anthropic-version 版本异常**：如果收到 `2023-06-01` 这样的过时版本号，且 User-Agent 声称是 `claude-code/2.1.86`，这是一个强矛盾信号
   - **请求体格式不一致**：model-family 的 OpenAI -> Claude 格式转换可能产生 Claude 原生客户端不会生成的请求结构（如缺少 `metadata` 字段、tools 数组格式异常等）
   - **Connection 复用模式**：model-family 到 clewdr 使用 Go HTTP/2 连接，clewdr 到 Claude API 使用 Rust HTTP/2 连接。双重代理的连接复用模式可能与单客户端不同

2. **请求频率的精细建模**

   多用户通过同一 token 的请求到达模式与单用户有本质差异：
   - 单用户：请求到达是**突发性**的（集中在思考和编码间隙），间隔呈长尾分布
   - 多用户聚合：请求到达趋向**泊松过程**（近似均匀随机到达），间隔呈指数分布
   - 蓝队可以通过拟合请求间隔的分布来区分

3. **SDK 版本一致性的精细化**

   真实 Claude Code 的 SDK 版本（x-stainless-runtime-version、anthropic-version 等）在每个大版本中是固定的。如果请求中出现跨版本的组合（如 claude-code/2.1.86 + anthropic-version/2023-06-01），这是一个高置信度的不一致信号。

### 4.3 双方都应关注的新维度

1. **rate limit 触发模式**

   真实案例中用户提到了"token rate limit handling"。多用户共享导致更频繁地触发 rate limit，而 rate limit 触发频率本身就是一个检测信号。正常单用户很少触发 rate limit（因为 Claude Code 的内置延迟足以避免），频繁触发表明并发使用。

2. **session cookie 的生命周期异常**

   正常用户的 session cookie 会定期刷新（浏览器行为）。反代使用的 cookie 可能长期不刷新（因为不经过正常的浏览器认证流程），这个"cookie 年龄"可以作为检测信号。

3. **对话上下文窗口的使用模式**

   正常 Claude Code 用户的上下文窗口使用是渐进式的（从短对话逐步延长）。多用户共享时，不同用户的对话长度分布更加均匀随机。蓝队可以分析同一 token 上不同 conversation 的上下文长度分布。

### 5.3 综合评价

蓝队继续保持优势（9.0 vs 8.5），差距维持在 0.5。双方都有持续进步，但进步的质量差异正在缩小。

**红队的核心进步**是从"被动防御"进化到"主动构建"：虚拟文件系统不是对蓝队规则的逐条修补，而是一个架构级的反制方案。分流策略更是跳出了"在反代层面伪装所有内容"的思维定式。这些进步使得红队在 PROBE-01 和 BEH-05 两个"已输"维度上扳回了部分失地。

**蓝队的核心进步**是从"可绕过的检测"进化到"不可绕过的挑战"：密码学挑战要求客户端实际执行计算，这从根本上区分了"有真实执行环境"和"仅做转发"的客户端。同时，BEH-07 API 状态机和 BILLING-01 账单异常是红队几乎无法完全规避的新维度。

**真实案例的关键启示：**

真实案例证明了三个核心观点：
1. clewdr 在单用户场景下的指纹伪装是可行的（个人使用没有问题）
2. 多用户共享是目前最大的暴露面（20 小时即被检出）
3. 多层代理（model-family）可能引入额外的指纹不一致，但不是根本原因

这对双方都有指导意义：
- **红队**应该把工程重心从"完善指纹伪装"转向"控制多用户行为的暴露面"（session 隔离、消费量限流、时间分布管理）
- **蓝队**应该加大在"使用画像"维度的投入（时间分布、消费量、并发会话），这是经真实案例验证的有效检测方向

**第四轮的关键战场预判：**

1. **PROBE-01 深度对抗**：红队是否会在反代上实现沙箱执行环境以应对密码学挑战？如果是，蓝队需要升级挑战的复杂度。
2. **多用户行为管理**：红队的 session 隔离 + 消费量限流能否将使用画像压到检测阈值以下？这是一个数学问题，取决于蓝队的阈值设置和红队的限流策略。
3. **API 状态机模拟**：红队需要补齐这个完全未覆盖的维度。
4. **model-family 链路整治**：红队需要正面回应多层代理的指纹问题，这可能涉及对 model-family 配置的建议或对 clewdr 的"强制覆盖"逻辑。
