## 一、最终可落地架构（精简三层）

裁判正确指出七层架构过于复杂。经过精简，最终架构保留三个核心层 + 一个基础设施层。

### 1.1 架构总览

```
┌─────────────────────────────────────────────────────┐
│                  基础设施层（独立）                    │
│         住宅代理 / Sticky IP / TLS 出口              │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────┴──────────────────────────────┐
│              Layer 1: 请求标准化层                     │
│  指纹伪装 + Header 硬编码 + JSON 序列化控制            │
│  + 探针检测/移除 + RP 内容分流                        │
├─────────────────────────────────────────────────────┤
│              Layer 2: 行为整形层                      │
│  Cookie 池管理 + 时序控制 + 使用量限流                 │
│  + API 状态机初始化                                  │
├─────────────────────────────────────────────────────┤
│              Layer 3: 协议适配层                      │
│  OpenAI 兼容端点 + SSE 流处理 + 错误恢复              │
└─────────────────────────────────────────────────────┘
```

### 1.2 Layer 1: 请求标准化层

**职责：** 确保发送给 Claude API 的每个请求在 header、body、序列化格式上与真实 Claude Code 客户端完全一致。同时负责内容层面的安全处理。

**技术选型：**

| 组件 | 技术方案 | 实现状态 |
|------|---------|---------|
| Header 硬编码 | Rust 常量 + `wreq::Client` 默认 header | **已落地**（clewdr `chat.rs` 中的 `CLAUDE_API_VERSION`, `CLAUDE_BETA_BASE` 等） |
| User-Agent 伪装 | 硬编码 `claude-code/{version}` + x-stainless-* 全套头 | **已落地**（clewdr `constants.rs`） |
| anthropic-beta 白名单过滤 | 只允许已知合法值通过，合并逻辑在 `extract_anthropic_beta_header()` | **已落地** |
| RequestNormalizer | 清理 OpenAI 残留字段、规范 system prompt 结构、强制 metadata | **可落地**（本次提出，需新增约 200 行 Rust） |
| JSON 序列化顺序控制 | 使用 `indexmap::IndexMap` 替代 `BTreeMap`，保证 key 插入序 | **可落地**（需审计 serde 配置） |
| 探针标签检测与移除 | 正则匹配非标准 XML 标签，从 system prompt 中剥离 | **可落地**（约 150 行 Rust） |
| RP 内容分流 | 检测叙事句式密度 > 40% 的请求，标记为高风险 | **理论方案**（需要 NLP 库，工程量较大） |

**配置示例（`clewdr.toml`）：**

```toml
[request_normalization]
# Claude Code 版本（需跟随上游更新）
claude_code_version = "2.1.86"
# 强制覆盖 max_tokens（0 = 不覆盖，使用上游值）
force_max_tokens = 16384
# 清理非标准字段
strip_openai_fields = true
# 探针检测（建议开启）
probe_detection = true
# 已知安全的 XML 标签白名单
safe_xml_tags = [
    "tool_definition", "tool_use", "tool_result",
    "project_context", "workspace", "git_info",
    "system_info", "user_preferences", "thinking",
]
```

### 1.3 Layer 2: 行为整形层

**职责：** 管理 Cookie 池，控制每个 Cookie 上的请求时序和使用量，使行为画像符合单用户模式。包含 API 状态机初始化。

**技术选型：**

| 组件 | 技术方案 | 实现状态 |
|------|---------|---------|
| Cookie 池管理 | `DashMap<CookieId, ManagedCookie>` + 用户绑定表 | **部分落地**（clewdr `cookie_actor.rs` 有基础 Cookie 管理，需扩展绑定逻辑） |
| 时序控制器 | 四状态机（ActiveCoding/Thinking/LongBreak/Offline）+ log-normal 间隔采样 | **可落地**（约 300 行 Rust，纯算法逻辑） |
| 使用量限流 | 每 Cookie 的小时/日/月 token 计数器 | **可落地**（约 100 行 Rust） |
| 活跃时段模拟 | 基于 Cookie 地区的时区感知活跃窗口 | **可落地**（约 150 行 Rust） |
| API 状态机 | Cookie 首次使用时执行 `GET organizations -> GET models -> count_tokens` | **可落地**（约 200 行 Rust） |
| 伴随流量 | 每 1-3 轮对话穿插 `count_tokens` 调用 | **可落地**（约 80 行 Rust） |

**配置示例（`clewdr.toml`）：**

```toml
[behavior_shaping]
# 严格模式：每 Cookie 最多 1 个并发用户（强烈推荐）
max_users_per_cookie = 1
# 每小时 token 上限（input + output）
hourly_token_limit = 30000
# 每日 token 上限
daily_token_limit = 400000
# 每小时请求数上限
hourly_request_limit = 30
# API 状态机初始化（首次使用自动执行）
api_init_enabled = true
# 伴随流量（每 N 轮对话穿插 count_tokens）
companion_traffic_interval = 2

[behavior_shaping.time_window]
# 工作日活跃时段（本地时间）
weekday_hours = [[9, 12], [13, 18], [20, 23]]
# 周末活跃时段
weekend_hours = [[11, 14], [16, 22]]
# 时区（auto = 从 Cookie 地区推断）
timezone = "auto"
```

### 1.4 Layer 3: 协议适配层

**职责：** 对外提供 OpenAI 兼容 API 端点，对内处理 SSE 流和错误恢复。这是消除 model-family 中间层的关键。

**技术选型：**

| 组件 | 技术方案 | 实现状态 |
|------|---------|---------|
| OpenAI 兼容端点 | `/v1/chat/completions` 路由 + OAI -> Claude 格式转换 | **已落地**（clewdr `router.rs` + `middleware/claude/` 目录） |
| SSE 流处理 | 标准 event type 转发 + 未知 event 静默消费 | **已落地**（clewdr `response.rs`） |
| 错误恢复 | 429 自动降速、5xx 重试、Cookie 健康检查 | **部分落地**（需增强 429 处理逻辑） |

**关键决策：消除 model-family 中间层。**

这是四轮攻防中反复验证的结论：

- 真实案例：个人 + OpenClaw -> clewdr 长期安全，多人 + model-family -> clewdr 20 小时封号
- 30% 的封号根因来自 model-family 引入的格式破坏
- clewdr 已内置 OpenAI 兼容端点，无需外部网关

推荐链路：
```
用户客户端 --> clewdr (OpenAI 兼容端点) --> Claude API
```

如需负载均衡或多实例，使用 nginx/caddy 的纯 TCP 代理模式（stream 模块），不做任何 HTTP 层修改。

### 1.5 基础设施层

| 组件 | 推荐方案 | 月成本估算 |
|------|---------|-----------|
| 住宅代理 | IPRoyal / Bright Data 的 Sticky Residential | $15-30/月（1GB 流量） |
| 服务器 | 任意 VPS（1 vCPU, 1GB RAM 足够） | $5-10/月 |
| 域名 + TLS | Let's Encrypt 自动续签 | $0 |

**住宅代理配置要点：**
- 每个 Cookie 绑定固定出口 IP（Sticky Session，24h+）
- 代理地区与 Cookie 注册地一致（通常 US West）
- 避免数据中心 IP（ASN 检测风险）

### 1.6 部署方案

**单用户模式（推荐，安全性最高）：**

```bash
# 一个 clewdr 实例，一个 Cookie，给自己用
CLEWDR_COOKIE="sessionKey=sk-ant-xxx"
CLEWDR_MAX_USERS_PER_COOKIE=1
CLEWDR_PROXY="socks5://user:pass@residential-proxy:port"
cargo run --release
```

运维要求：
- Claude Code 版本更新后 48h 内更新 `constants.rs` 中的版本号（约每 1-2 周一次）
- 监控 Cookie 健康状态（429 频率、响应错误率）

**多用户模式（高风险，不推荐）：**

```bash
# 需要 Cookie 数量 >= 用户数量
CLEWDR_COOKIE_POOL="sk-ant-xxx1,sk-ant-xxx2,sk-ant-xxx3"
CLEWDR_MAX_USERS_PER_COOKIE=1  # 仍然建议 1:1
CLEWDR_BEHAVIOR_SHAPING=true
CLEWDR_HOURLY_TOKEN_LIMIT=30000
cargo run --release
```

运维要求（在单用户基础上额外）：
- 持续补充 Cookie 池（预期每个 Cookie 寿命 1-4 周）
- 监控每个 Cookie 的使用量和健康状态
- 时序整形和使用量限流需要持续调参

## 二、成本效益分析

裁判判定："攻防的决定性因素已从纯技术转向经济学。" 以下是诚实的成本分析。

### 2.1 反代运营总成本

#### 单用户模式（1 人使用）

| 成本项 | 月成本 | 说明 |
|--------|--------|------|
| Cookie/订阅 | $20/月（Claude Pro）或 $0（免费额度） | 一个 Pro 订阅 = 一个 Cookie |
| 服务器 | $5-10/月 | 最低配 VPS |
| 住宅代理 | $15-30/月 | Sticky Residential 1GB |
| 运维人力 | ~2h/月 | 版本追踪 + 问题排查 |
| **月总成本** | **$40-60/月** + 人力 | |

#### 多用户模式（N 人共享）

| 成本项 | 月成本 | 说明 |
|--------|--------|------|
| Cookie/订阅 | $20 x N/月（1:1 模式） | 每用户一个 Cookie |
| 服务器 | $10-20/月 | 需更多内存管理状态 |
| 住宅代理 | $30-100/月 | 每 Cookie 独立 IP |
| 运维人力 | ~8-20h/月 | Cookie 补充 + 监控 + 调参 |
| Cookie 损耗 | $20 x 封号率/月 | 预期 10-30% 月损耗率 |
| **月每用户成本** | **$30-50/用户** + 运维 | |

### 2.2 正规使用成本

| 方案 | 月成本/用户 | 限制 |
|------|-----------|------|
| Claude Pro | $20/月 | 有使用限额 |
| Claude Max (5x) | $100/月 | 5 倍额度 |
| Claude Max (20x) | $200/月 | 20 倍额度，接近无限 |
| Claude API (按量) | $3/M input, $15/M output | 无限制，按量计费 |
| Claude Code 内置 (Pro 订阅) | $20/月 | Claude Code 自带，有额度 |

### 2.3 经济可行性分析

#### 单用户场景

| 指标 | 反代 | 正规订阅 |
|------|------|---------|
| 月成本 | $40-60 | $20 (Pro) / $100 (Max 5x) |
| 可用性 | 95%（Cookie 风险） | 99.9% |
| 使用限额 | 受限于限流参数 | Pro 有限额，Max 充裕 |
| 运维负担 | 2h/月 | 零 |
| 法律风险 | 存在（违反 ToS） | 无 |

**结论：单用户反代在经济上不合理。** 除非目标是绕过内容限制（RP 场景）或地域封锁，否则直接订阅 Pro/Max 更便宜、更可靠。反代的唯一经济合理性在于：用 $20 的 Pro Cookie 获得超出 Pro 限额的使用量（即 $20 的成本获得 $100-200 级别的额度）。但蓝队的使用量检测（BILLING-01）和限流对策直接打击了这一点。

#### 多用户场景

| 用户数 | 反代月成本/用户 | 正规月成本/用户 | 反代优势 |
|--------|-------------|-------------|---------|
| 2 人 | $35-45 | $20 (Pro) | 无（更贵） |
| 5 人 | $30-40 | $20 (Pro) | 无（更贵且高风险） |
| 10 人 | $25-35 | $20 (Pro) | 极微弱（但 Cookie 损耗可能更高） |
| 20+ 人 | $25-30 | $20 (Pro) | 无（蓝队 2-4h 检出，Cookie 损耗激增） |

**结论：多用户反代在 1:1 模式（每用户一个 Cookie）下永远不比正规订阅便宜。** 蓝队的检测体系已成功将反代推入 1:1 模式，经济模型彻底崩溃。

#### 唯一有经济意义的场景

1. **绕过地域封锁**：用户所在地区无法直接订阅 Claude，反代是唯一选择。成本高于正规价但别无他法。
2. **绕过内容限制**：RP/创意写作场景，用户愿意为"无审核"体验支付溢价。但蓝队 BEH-05 对 RP 内容的 55-65% 检出率意味着 Cookie 寿命显著缩短。
3. **利用 Cookie 额度差**：用 Pro 订阅的 Cookie 但通过反代消费远超 Pro 限额的 token。这取决于 Anthropic 对 Pro 级别的限额执行力度。

### 2.4 生存率与预期寿命

| 场景 | 蓝队检测级别 | 预期 Cookie 寿命 | 月生存率 |
|------|------------|----------------|---------|
| 单用户 + 编程 | 被动检测分 16.2 | 3-6 个月 | 80-90% |
| 单用户 + RP | 被动检测分 22.2 | 1-3 个月 | 50-70% |
| 多用户 (3-5人) + 完整整形 | 被动检测分 25-33 | 1-4 周 | 20-40% |
| 多用户 (5+) + model-family | 被动检测分 33.7 | 1-3 天 | < 10% |

### 2.5 经济不可行的临界条件

反代在经济上不可行的条件（满足任一即不可行）：

1. **Cookie 月损耗率 > 50%**：需要持续补充 Cookie，成本不可控
2. **正规订阅降价到 $10/月以下**：反代成本优势完全消失
3. **Anthropic 启用设备绑定认证**：Cookie 无法跨设备使用，反代链路断裂
4. **每用户需要独立 Cookie**（当前状态）：多用户模式的成本优势不存在
5. **运维人力成本 > $20/h**：版本追踪和问题排查的人力投入使反代更贵

**诚实结论：在蓝队检测体系完备的假设下，反代的经济可行性仅存在于"绕过地域/内容限制的溢价支付"场景。在纯成本竞争维度，反代已经输了。**

## 三、不可解决的风险清单

以下是在当前架构下永远无法完美解决的检测维度。

### 3.1 密码学探针（PROBE-01）

**风险等级：中**

**问题核心：** 蓝队可在 system prompt 中注入要求 Claude 执行 `sha256sum` 等计算的指令。如果反代拦截了 system prompt 中的探针块，Claude 的响应中不会包含验证结果，蓝队可以据此判断探针被移除。如果不拦截，反代需要在沙箱中执行密码学计算并注入正确结果。

**决策：缓解（双轨策略）**
- 主策略：检测并移除可疑探针标签（已知标签白名单过滤），成功率约 70%
- 兜底策略：沙箱执行密码学命令，成功率约 80%
- 综合检出率：25-40%（裁判修正值 30-45%）
- **永远无法完美解决的原因：** 蓝队可以将探针隐藏在合法的 system prompt 格式中（如使用 `<workspace>` 等已知标签包装验证指令），使红队无法区分探针和正常内容。更进一步，蓝队可以将验证逻辑分散在多个合法工具调用的交互中，形成多阶段验证链，红队无法在不破坏正常功能的前提下全部拦截。

### 3.2 内容画像 / RP 语义检测（BEH-05）

**风险等级：高（RP 场景）/ 低（编程场景）**

**问题核心：** RP/创意写作内容具有不可消除的语义特征 -- 叙事句式密度、情感词密度、对话结构对称性。这些特征存在于请求体的 messages 内容中，反代无法在不改变语义的前提下消除它们。

**决策：规避**
- 高风险内容（RP 叙事密度 > 40%）标记为危险，建议使用非 Claude Code 通道
- 编程场景不受影响（BEH-05 分数低）
- **永远无法完美解决的原因：** 内容是用户生成的，反代作为透明代理层无法改写用户内容。任何改写都会损害用户体验。这是反代架构的根本限制。

### 3.3 多用户行为聚合（BEH-06）

**风险等级：高（多用户场景）/ 无（单用户场景）**

**问题核心：** 多个独立用户的请求在统计上不可能与单用户完全一致。即使做了时序整形，多用户的请求内容多样性（不同项目、不同语言、不同代码风格、不同 session 指纹）仍然可以被区分。

**决策：缓解 + 接受**
- 缓解：严格 1:1 模式（每 Cookie 单用户）消除大部分行为聚合信号
- 接受：1:1 模式意味着多用户场景的经济模型崩溃
- **永远无法完美解决的原因：** 信息论极限。多用户的请求内容天然具有更高的熵和多样性。蓝队的 session 指纹（system prompt 长度、tool 集合、语言特征）可以跨请求关联，红队无法统一所有下游用户的请求特征。唯一的解法是 1:1 -- 但这本身就是蓝队的胜利。

### 3.4 经济壁垒

**风险等级：致命（战略层面）**

**问题核心：** 蓝队不需要 100% 检出。只要检测压力迫使反代采用 1:1 模式 + 消费量限流 + 复杂架构，反代的运营成本就趋近于正规使用。

**决策：接受**
- 这是不可对抗的战略壁垒
- **永远无法解决的原因：** 这不是技术问题，而是经济学定律。当"绕过成本 >= 正规成本"时，绕过失去意义。蓝队的每一次检测加强都提高了红队的运营成本，而红队无法降低这个成本（因为 Cookie、服务器、代理都是刚性成本）。

### 3.5 TLS 指纹（NET-01）

**风险等级：低**

**问题核心：** clewdr 使用 rustls，其 TLS ClientHello 与 Claude Code 使用的 BoringSSL 存在可检测的差异（cipher suite 顺序、扩展列表、GREASE 值模式）。

**决策：缓解（长期接受）**
- wreq/rustls 可以配置部分参数接近 BoringSSL
- CDN 和中间设备的干扰降低了 TLS 指纹的可靠性
- 不致命：裁判确认蓝队无法仅凭 TLS 指纹做出高置信度判定
- **永远无法完美解决的原因：** 除非 clewdr 切换到 BoringSSL（通过 FFI 绑定），rustls 的 ClientHello 与 BoringSSL 永远不会完全一致。但 TLS 指纹在实际中的信噪比有限，不是致命风险。

### 3.6 风险汇总矩阵

| 风险 | 影响 | 可控性 | 决策 | 剩余检出率 |
|------|------|--------|------|-----------|
| 密码学探针 | 触发主动调查 | 部分可控 | 缓解 | 30-45% |
| RP 内容画像 | 被动检测升分 | 不可控 | 规避场景 | 55-65%（RP 场景） |
| 多用户行为 | 被动检测升分 | 通过 1:1 可控 | 接受经济代价 | 20-35%（已整形） |
| 经济壁垒 | 模型不可行 | 不可控 | 接受 | N/A |
| TLS 指纹 | 辅助信号 | 部分可控 | 长期缓解 | 30-40% |

## 四、对蓝队终极方案的评估

### 4.1 蓝队 2 小时快速检测的有效性评估

**在我的最终架构下，蓝队的 2 小时快速检测是否有效？**

| 检测组件 | 对单用户模式的有效性 | 对多用户 1:1 模式的有效性 |
|---------|-------------------|------------------------|
| CV 分析（变异系数） | **无效。** 单用户请求天然是突发性长尾分布，CV > 2.0 | **无效。** 1:1 模式下每 Cookie 仍是单用户模式 |
| KS 检验（分布检验） | **无效。** 请求间隔天然不是泊松过程 | **无效。** 同上 |
| Session 指纹多样性 | **无效。** 单用户的 session 指纹自然一致 | **低效。** 1:1 模式下每 Cookie 只有一个用户的指纹 |
| 累积消费量 | **低效。** 限流参数控制在合理范围内 | **低效。** 同上 |
| 突发-等待模式检测 | **无效。** 单用户天然有此模式 | **无效。** 同上 |

**结论：在严格 1:1 模式下，蓝队的 2 小时快速检测基本失效。** 但代价是反代退化为"1 Cookie 1 用户"的 API 兼容层，经济模型崩溃。蓝队的真正胜利不在于"技术检出"，而在于"迫使红队进入 1:1 模式"。

**蓝队 2 小时检测仍然有效的场景：**
- 红队使用宽松模式（每 Cookie 2+ 用户）：有效，2-8 小时检出
- 红队通过 model-family 链路：有效，MLP 系列 + 行为分析双重打击
- 红队未实施时序整形：有效，CV 分析 30 分钟即可检出

### 4.2 最让红队头疼的蓝队检测

按痛苦程度排序：

**第 1 名：经济学战略（成本趋近）**

这不是一个具体的检测规则，而是蓝队整个检测体系产生的战略效果。每增加一条检测规则，红队就需要增加一层防御，增加一项成本。最终红队的运营成本被推到与正规订阅持平。这是**不可逆的**、**不可绕过的**战略武器。

**第 2 名：BEH-05 RP 内容语义检测**

RP 内容的语义特征（叙事句式、情感词、第一/第三人称交替、动作描述密度）在反代架构层面无法消除。红队唯一的应对是"不使用"或"分流到其他通道"，这直接缩小了反代的适用范围。对于以 RP 为核心需求的用户群体，这是致命打击。

**第 3 名：BEH-06 多用户行为聚合 + 组织级分析**

蓝队的组织级分析可以跨 Cookie 关联。如果同一组织下有 5+ 个 Cookie 呈现高度相似的使用签名（都经过同一 clewdr 实例的时序整形，产生相似的 log-normal 间隔分布参数），蓝队可以在组织级别触发调查。红队需要为每个 Cookie 使用不同的时序参数来对抗，进一步增加复杂度。

**第 4 名：PROBE-01 密码学挑战（反 VFS 变体）**

蓝队的跨工具一致性验证（在 Bash 中写文件、用 Read 读取、检查 stat 元数据）设计精巧。红队的沙箱方案需要维护完整的文件系统状态一致性，工程复杂度极高。每增加一种跨工具验证模式，红队的沙箱就需要扩展。

**第 5 名：版本追踪竞速**

Claude Code 约每 1-2 周更新。每次更新后存在一个窗口期（48h 内），红队的版本号与最新 Claude Code 不匹配。蓝队的 MLP-02 在窗口期内有 40-60% 的检出率。红队必须投入持续的运维人力来跟踪版本变化。

### 4.3 蓝队经济学战略的影响

蓝队的成本趋近战略对红队的影响是根本性的：

```
蓝队检测强度 ↑
  → 红队需要 1:1 模式（成本 ↑）
  → 红队需要限流（吞吐量 ↓，服务质量 ↓）
  → 红队需要复杂架构（运维成本 ↑）
  → 红队需要持续版本追踪（人力成本 ↑）
  → 反代总成本 ≈ 正规订阅
  → 反代失去经济意义
```

这个因果链是不可打断的。红队在每个环节的反制都只能降低成本增速，无法逆转成本上升趋势。蓝队不需要完美检出，只需要持续施压。

## 五、给 clewdr 项目的具体建议

基于五轮攻防的所有知识，以下建议按优先级排序。

### P0: 关键 -- 立即实施

#### 5.1 消除 model-family 中间层

**现状：** clewdr 已内置 OpenAI 兼容端点。用户通过 model-family 中转是 30% 封号根因。

**建议：**
- 在文档和 README 中明确推荐"用户直连 clewdr"的部署方式
- 如用户需要多模型网关功能，建议在 clewdr 上游使用纯 TCP 代理（nginx stream）
- 在 `clewdr.toml` 中新增 `warn_on_proxy_headers = true`，当检测到上游代理特征（如 `X-Forwarded-For`、Go HTTP client UA）时输出警告日志

**工程量：** 约 20 行配置检测 + 文档更新

#### 5.2 JSON 序列化顺序控制

**现状：** 裁判指出 serde 默认可能使用 `BTreeMap`（字母序），与 Claude Code 的 JS 对象（插入序）不一致。蓝队 MLP-03 可检测字母序 JSON key。

**建议：**
- 审计所有涉及 Claude API 请求体序列化的 struct，确保使用 `indexmap::IndexMap` 或 `serde_json::Map`（保持插入序）
- 在 `CreateMessageParams` 等核心类型中，用 `#[serde(serialize_with = ...)]` 自定义序列化顺序，匹配 Claude Code 的字段顺序

**工程量：** 约 50-100 行代码修改

#### 5.3 持续版本追踪机制

**现状：** `constants.rs` 中硬编码了 Claude Code 版本号和 beta header。每次 Claude Code 更新后需手动修改。

**建议：**
- 将版本常量集中到 `constants.rs`（已部分实现），确保单点修改
- 编写一个自动化脚本（CI/CD 或 GitHub Action），定期检查 Claude Code 最新版本（通过 npm registry 查询 `@anthropic-ai/claude-code` 的 latest version），发现更新时自动创建 Issue 或 PR
- 在版本常量旁添加注释标注"上次更新日期"和"对应 Claude Code 版本"

**工程量：** 约 50 行脚本 + CI 配置

### P1: 重要 -- 本月实施

#### 5.4 RequestNormalizer 落地

**建议：**
- 在请求发送前新增标准化步骤，清理所有非 Claude Code 标准字段
- 具体实现：
  - 清理 OpenAI 残留字段（`frequency_penalty`, `presence_penalty`, `logit_bias`, `n`, `seed`, `logprobs`）
  - 强制 `stream = true`
  - 规范 `metadata` 字段（确保包含 `user_id`）
  - 规范 `system` 字段格式（如果是字符串，转为 content block 数组；确保包含 `cache_control`）

**实现位置：** `src/claude_code_state/chat.rs` 或新建 `src/claude_code_state/normalize.rs`

**工程量：** 约 200 行 Rust

#### 5.5 使用量限流

**建议：**
- 在 `CookieActor` 中增加每 Cookie 的 token 计数器
- 实现每小时 30k token、每日 400k token 的软限制
- 超限时返回 429 给下游（而非继续向 Claude API 发送请求被检测）
- 配置化限流参数，允许用户根据自身情况调整

**实现位置：** `src/services/cookie_actor.rs`

**工程量：** 约 100 行 Rust

#### 5.6 anthropic-beta 白名单过滤

**现状：** `extract_anthropic_beta_header()` 从上游提取并合并 beta 值。如果上游传入了非法 beta 值，会被包含在最终请求中。

**建议：**
- 白名单模式：只允许已知合法的 beta 值通过
- 当前已知合法值：`claude-code-20250219`, `oauth-2025-04-20`, `interleaved-thinking-2025-05-14`, `extended-cache-ttl-2025-04-11`
- 将白名单与版本常量放在一起，随版本更新同步维护

**工程量：** 约 30 行 Rust

### P2: 有价值 -- 季度内实施

#### 5.7 API 状态机初始化

**建议：**
- Cookie 首次使用时，在发送 messages 请求前先执行：
  1. `GET /api/organizations`
  2. `GET /api/organizations/{org_id}/models`（70% 概率）
  3. `POST /api/messages/count_tokens`（系统提示词 token 计数）
- 之后每 1-3 轮对话穿插一次 `count_tokens` 伴随流量

**工程量：** 约 300 行 Rust

#### 5.8 探针标签检测

**建议：**
- 在 system prompt 处理阶段，检测非标准 XML 标签
- 维护 Claude Code 已知标签的白名单
- 对未知标签内容进行分析：如果包含 shell 命令、hash 计算等模式，判定为探针并移除
- 记录被移除的探针用于调试

**工程量：** 约 150 行 Rust

#### 5.9 429 预防性限速

**建议：**

- 连续 3 次 429 后暂停该 Cookie 使用 30 分钟
- 429 频率本身是蓝队的检测信号（裁判第 3 轮指出），必须预防

**工程量：** 约 80 行 Rust，部分已有基础实现

3. **RP/创意写作高强度使用**：BEH-05 语义检测 55-65% 检出率，Cookie 寿命显著缩短
4. **不配置住宅代理的部署**：数据中心 IP 容易被 ASN 检测，GEO-01 风险

## 六、攻防长期均衡状态

### 6.1 最终收敛态

经过五轮对抗，攻防的长期均衡已经清晰：

**蓝队无法实现 100% 检出。** 在单用户编程场景下，红队的被动检测分约 16.2，远低于任何合理阈值。蓝队要把阈值降到 16 以下会导致大量正常用户被误触发。稳态检出率约 10-20%（单用户编程场景）。

**红队无法实现 0% 检出。** TLS 指纹、版本追踪延迟、偶发的探针挑战构成了不可消除的底线风险。稳态存活率约 80-90%（单用户编程场景，含版本追踪的运维投入）。

**均衡点在经济学而非技术。** 技术上可行不等于经济上合理。蓝队已将反代推入"高成本低收益"的运营模式。

### 6.2 工程投入对比

**如果 Anthropic 投入 X 工程师-月建设检测系统：**

| Anthropic 投入 | 红队需要的维持投入 | 倍率 |
|--------------|-----------------|------|
| 1 工程师-月（基础规则） | 0.5 工程师-月 | 0.5x |
| 3 工程师-月（完整规则集） | 2 工程师-月 | 0.67x |
| 6 工程师-月（ML 模型 + 自动化） | 4 工程师-月 | 0.67x |
| 12 工程师-月（全套运营体系） | 10+ 工程师-月 | 0.83x |

红队的维持投入随蓝队投入近线性增长。但蓝队的投入是一次性的（建设完检测系统后边际成本低），而红队的投入是持续性的（每次版本更新、每次规则变化都需要响应）。长期来看，蓝队在投入产出比上占优。

### 6.3 最终判定

**反代作为技术实践是可行的。** clewdr 在单用户场景下的指纹伪装已经成熟，被动检测分远低于触发阈值。

**反代作为商业模式是不可行的。** 蓝队的检测体系已将多用户共享模式推入经济不可行区间。反代只能作为个人工具（1:1 模式）生存，但在 1:1 模式下，其经济优势相比正规订阅微乎其微甚至为负。

**反代的残余价值在于"访问层"而非"成本层"。** 它的意义不在于省钱，而在于：提供 OpenAI 兼容 API 接口（兼容性）、绕过地域限制（可达性）、提供额外的请求控制能力（灵活性）。clewdr 应将定位从"省钱工具"调整为"兼容性网关"。
