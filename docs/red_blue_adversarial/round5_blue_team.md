### 1.2 技术选型

| 组件 | 技术选型 | 理由 |
|------|---------|------|
| 实时评分引擎 | **嵌入 API Gateway (Rust/Go)** | 零额外网络跳转，P99 延迟 < 5ms |
| 实时状态存储 | **Redis Cluster** | 滑动窗口计数器、请求间隔序列、session 指纹集合 |
| 事件流 | **Kafka** | 异步写入，解耦评分与离线分析 |
| 离线分析 | **ClickHouse** | 列式存储，适合时序聚合和分布检验 |
| ML 模型服务 | **不使用** (见 1.3 说明) | 规则引擎 + 统计检验足够，ML 增加运维复杂度但边际收益低 |
| 告警/工单 | **PagerDuty + 内部 SIEM** | 与现有安全运维对接 |
| 日志归档 | **S3 + Parquet** | 低成本长期存储，支持 Athena 回溯查询 |

**为什么不用 ML 模型：** 四轮攻防的核心结论是，最有效的检测信号（多用户行为聚合、RP 语义特征、请求格式异常）都可以用统计检验和规则引擎实现。ML 模型引入了训练数据偏差、模型更新延迟、解释性差等问题，而在 recall 上的边际提升不足以覆盖这些成本。唯一值得 ML 化的是 BEH-05（RP 内容检测），可以在 MVP 后用轻量分类器替换关键词规则。

### 1.3 核心规则精选：Top 10 ROI 排序

从四轮攻防中积累的 30+ 条规则中，按 `(检出贡献 x 可靠性) / (实现成本 + 误报风险)` 筛选出 ROI 最高的 10 条：

| 优先级 | 规则 ID | 名称 | 检出率 | 误报率 | 实现成本 | 部署阶段 |
|--------|---------|------|--------|--------|---------|---------|
| **P0** | BEH-06v3 | 请求到达 CV 分析 | 多用户 60-80% | < 0.05% | 低 | MVP |
| **P0** | USAGE-01 | 2h 滑动窗口消费量 | 多用户 50-70% | < 0.1% | 低 | MVP |
| **P1** | BEH-05v2 | RP 内容语义检测 | RP 场景 55-65% | < 0.5% | 中 | MVP |
| **P1** | SESSION-01 | Session 指纹多样性 | 多用户 40-60% | < 0.2% | 低 | MVP |
| **P1** | BILLING-02 | 组织级消费异常关联 | 多cookie 30-45% | < 0.3% | 中 | Phase 2 |
| **P2** | NET-01 | TLS 指纹异常 | 稳态 15-25% | < 0.1% | 中 | Phase 2 |
| **P2** | BEH-07v2 | API 状态机初始化缺失 | 版本窗口期 40-60% | < 0.05% | 低 | MVP |
| **P2** | MLP-01 | 格式转换残留检测 | model-family 链路 30-50% | < 0.2% | 低 | MVP |
| **P3** | PROBE-01v2 | 主动工具探测（密码学挑战） | 被触发时 30-45% | 0% (主动) | 高 | Phase 3 |
| **P3** | BURST-01 | 突发-等待模式缺失检测 | 多用户 25-40% | < 0.3% | 低 | Phase 2 |

**规则设计原则：**
- P0 规则能独立触发 MONITOR，两条 P0 同时触发可直接 CHALLENGE
- P1 规则作为 P0 的增强信号，提升置信度
- P2 规则在特定场景下有效（版本窗口期、特定链路），作为辅助
- P3 规则成本较高或检出率有限，但在 P0+P1 积累分数后提供关键确认

### 1.4 评分模型最终版

```python
# 评分权重（裁判修正后的版本）
LAYER_WEIGHTS = {
    "NET":     0.10,  # TLS/HTTP 网络层指纹
    "REQ":     0.08,  # 请求格式规范性
    "BEH":     0.25,  # 行为画像（最大权重，覆盖 CV 分析、状态机、突发模式）
    "CONTENT": 0.15,  # 内容语义（RP 检测主阵地）
    "USAGE":   0.20,  # 消费量 + 时间覆盖度（裁判建议从 0.25 调至 0.20）
    "META":    0.12,  # 组织级关联分析
    "MLP":     0.10,  # 多层代理专项（仅对特定链路有效）
}

# 各层取 max 后加权求和
def calculate_score(layer_scores: dict) -> float:
    total = 0.0
    for layer, weight in LAYER_WEIGHTS.items():
        if layer in layer_scores:
            total += max(layer_scores[layer]) * weight
    return total

# 决策阈值
THRESHOLDS = {
    "ALLOW":     (0, 25),
    "MONITOR":   (25, 40),
    "CHALLENGE": (40, 60),
    "RESTRICT":  (60, 80),
    "BLOCK":     (80, 100),
}
```

### 1.5 部署方案

**容器化：**

```yaml
# Kubernetes 部署拓扑
apiVersion: apps/v1
kind: Deployment
metadata:
  name: abuse-detection-engine
spec:
  replicas: 3  # 至少 3 副本，跨 AZ 部署
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  template:
    spec:
      containers:
      - name: scoring-engine
        image: abuse-detection:v1.0
        resources:
          requests:
            cpu: "500m"
            memory: "1Gi"
          limits:
            cpu: "2"
            memory: "4Gi"
        env:
        - name: REDIS_CLUSTER_URL
          valueFrom:
            secretKeyRef:
              name: redis-credentials
              key: url
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /readyz
            port: 8080
          periodSeconds: 5
```

**扩缩容策略：**
- 基于 API Gateway QPS 的 HPA（水平自动伸缩）：QPS > 10k/副本时扩容
- Redis Cluster 分片数随 token 数量线性增长（每 100k 活跃 token 一个分片）
- ClickHouse 使用 ReplicatedMergeTree，按天分区，30 天热数据 + 365 天冷存储

**高可用：**
- 评分引擎无状态，依赖 Redis 和 Kafka；Redis 故障时降级为"仅记录不评分"
- Kafka 消费者组保证每条事件至少处理一次
- 所有阈值通过配置中心动态下发，无需重启服务

### 1.6 运维 SOP

| 场景 | SOP |
|------|-----|
| 规则误报率突增 | 1. 自动告警（误报率 > 0.3%） → 2. 值班安全工程师确认 → 3. 动态降低该规则权重 → 4. 提工单分析根因 → 5. 修正规则逻辑并回归测试 |

### 2.2 检测收益估算

**假设：**
- Anthropic Claude Code Max 订阅价格：$200/用户/月
- 活跃反代服务约 50-200 个 token/cookie 被非法共享
- 每个 cookie 平均服务 5-10 个下游用户
- 平均每个 cookie 月消费量等价于 3-5 个正规用户

| 场景 | 未检测损失 | 检测后损失 | 检测减少的损失 |
|------|-----------|-----------|--------------|
| 100 个被滥用 cookie，各服务 5 人 | 500 人 x $200 = $100k/月 | 检出 60% = 200 人逃逸 x $200 = $40k/月 | **$60k/月 = $720k/年** |
| 保守估计：50 个 cookie，各服务 3 人 | $30k/月 | 检出 50% = $15k/月 | **$180k/年** |
| 乐观估计：200 个 cookie，各服务 8 人 | $320k/月 | 检出 70% = $96k/月 | **$2,688k/年** |

### 2.3 ROI 分析

| 估计 | 年检测收益 | 年运营成本 | ROI |
|------|-----------|-----------|-----|
| 保守 | $180k | $88k | **2.0x** |
| 基准 | $720k | $88k | **8.2x** |
| 乐观 | $2,688k | $88k | **30.5x** |

**结论：即使在保守估计下，检测系统的 ROI 也大于 1。** 系统在运营 6 个月后即可收回全部建设成本。

### 2.4 误报处理的人力成本

| 指标 | 数值 |
|------|------|
| 日活跃 token/cookie 数 | 50,000（假设） |
| 目标误报率 | < 0.1% |
| 每日误报 token 数 | < 50 |
| 每个误报处理时间 | 15-30 分钟（L1 查看评分明细 + 决定） |
| 每日误报处理人时 | 12.5-25 小时 |
| 需要的 L1 分析师 | 2-3 人（含自动化工具后可降至 1-2 人） |

**关键风险：** 误封一个企业大客户的品牌损失远大于放过一个反代用户。因此 BLOCK 操作必须经过人工确认（CHALLENGE/RESTRICT 可自动化，BLOCK 需要 L2 审批）。

### 2.5 与直接限制（Rate Limiting）的成本对比

| 方案 | 实现成本 | 精确度 | 用户体验影响 | 反代抑制效果 |
|------|---------|--------|------------|------------|
| 简单 Rate Limiting | 极低（已有） | 低 | 影响重度合法用户 | 低（反代可分散到多 cookie） |
| 本方案（行为检测） | 中 | 中-高 | 极低（仅影响真正的反代） | 中-高（迫使反代采用高成本 1:1 模式） |
| 设备绑定/硬件认证 | 高 | 高 | 中（增加登录摩擦） | 高（但降低用户满意度） |
| 不做任何限制 | 零 | N/A | 零 | 零 |

**推荐：Rate Limiting 作为基线保护（已有），行为检测作为精准防御层叠加。** 两者互补而非替代关系。Rate Limiting 防止极端滥用（如 DDoS 级别的请求量），行为检测识别精心伪装的反代。

## 三、不可检测的场景清单（诚实评估）

四轮攻防的核心教训是：**检测系统不可能 100% 检出所有反代使用。** 以下场景我们承认永远无法可靠检测：

### 3.1 永远无法检测的场景

| 场景 | 检出率 | 原因 |
|------|--------|------|
| **单用户 + 单 cookie + 编程用途** | < 10% | 这与正规 Claude Code 使用在统计上不可区分。行为画像、消费量、请求模式全部在正常范围内。这是红队不可攻破的壁垒。 |
| **完美指纹模拟 + 1:1 映射** | < 15% | 当 clewdr 的指纹伪装足够精确，且每个 cookie 只服务一个用户时，被动检测几乎完全失效。仅 NET-01 TLS 指纹和偶发的版本追踪窗口期提供微弱信号。 |
| **低频使用（每天 < 50 请求）** | < 5% | 统计检验需要足够的样本量。低频使用意味着 CV 分析、KS 检验、session 指纹多样性等核心规则都无法积累有意义的数据。 |
| **合法使用场景的边界** | N/A | 一个正规用户通过 SSH 在远程服务器上运行 Claude Code，其 TLS 指纹、网络路径与反代相似。一个重度开源维护者在 hackathon 中 16 小时连续使用，其消费量与多用户共享相似。我们无法也不应该检测这些用户。 |

### 3.2 理论可检测但实际困难的场景

| 场景 | 理论检出率 | 实际检出率 | 瓶颈 |
|------|-----------|-----------|------|
| 2-3 用户/cookie + 完整时序整形 | 40-50% | 20-30% | 红队时序整形有效降低 CV 值，KS 检验需要 30+ 样本（低频场景积累慢） |
| 绕过 model-family 的 clewdr 直连 | 30-40% | 15-25% | MLP 系列规则完全失效，仅依赖 BEH+USAGE 层 |
| RP 使用但内容经过深度改写 | 55-65% | 30-40% | 如果红队投入资源做 LLM 级别的内容改写（将 RP 句式转为技术文档句式），BEH-05 的语义检测会大幅削弱 |

### 3.3 关键认知

**检测系统的目标不是 100% 检出，而是让反代的运营成本高到失去经济意义。**

当我们的检测压力迫使红队采用以下配置时，我们就已经赢了：

```
红队被迫采用的"安全配置"：
  - 1 cookie : 1 用户（消除多用户行为信号）
  - 每日 < 400k tokens/cookie（避免消费量异常）
  - 活跃时段限制（14h/天而非 24h）
  - 完整 API 状态机模拟（额外 API 调用消耗 token）
  - 请求时序整形（排队等待降低吞吐量）
  - 持续版本追踪（每 1-2 周更新指纹）
  - 住宅代理（$50-200/月/IP）
```

在这种配置下，每个"用户"需要一个独立 cookie + 一个住宅 IP + 有限的使用额度。反代的"一个订阅服务多人"的商业模型彻底崩溃。

## 四、对红队终极方案的评估

### 4.1 红队精简后的 3-4 层架构评估

裁判在第四轮建议红队将七层架构精简为三个核心层。预期红队终极方案：

| 层级 | 功能 | 蓝队检出能力 |
|------|------|------------|
| **请求层**（标准化 + 指纹伪装） | UA、headers、beta、API version 伪装；清理 OpenAI 残留字段；JSON 序列化规范化 | **低**。clewdr 硬编码的指纹已足够精确。仅 TLS 指纹（rustls vs BoringSSL）提供微弱信号。检出贡献 < 5 分。 |
| **行为层**（Cookie 管理 + 时序控制 + API 状态机） | 1:1 cookie 绑定；log-normal 时序整形；初始化序列模拟；伴随流量生成 | **中等**。严格模式下 BEH-06 几乎失效（CV 自然 > 2.0）；但组织级分析（BILLING-02/META）仍可跨 cookie 关联。检出贡献 5-15 分。 |
| **内容层**（RP 清洗 + 工具拦截） | 格式标记替换；叙事动词降密度；探针沙箱 | **中-高**。RP 语义残留是红队的结构性弱点。即使清洗了 `*动作*` 标记，叙事句式密度、场景延续模式、角色实体共享等深层特征不可消除。检出贡献 10-25 分（RP 场景）。 |

**综合评估：**

| 红队配置 | 蓝队被动评分 | 结论 |
|---------|------------|------|
| 单用户 + 编程用途 + 严格模式 | 12-18 分 | 安全通过。蓝队无有效检出手段。 |
| 单用户 + RP 用途 + 严格模式 | 18-28 分 | 边界区域。取决于 RP 内容的深度和 BEH-05 的阈值设定。 |
| 3 用户/cookie + 编程用途 | 22-35 分 | MONITOR 区间。4-8 小时后可能触发 CHALLENGE。 |
| 5+ 用户/cookie + model-family 链路 | 30-45 分 | CHALLENGE 区间。2-4 小时内高概率被检出。 |

### 4.2 红队"1 cookie/用户 + 严格模式"下蓝队的残余手段

在红队的最优配置下，蓝队仅剩以下微弱信号：

1. **NET-01 TLS 指纹**（持续信号，但单独不够触发动作）
   - rustls 的 TLS ClientHello 与 BoringSSL 有细微差异
   - 但 CDN/负载均衡的噪声使得此信号不可靠
   - 贡献：3-5 分

2. **版本追踪竞速窗口**（间歇信号）
   - Claude Code 每 1-2 周更新，红队需要跟进
   - 窗口期内 BEH-07/MLP-02 有效
   - 贡献：窗口期内 +10-20 分，稳态 0 分

3. **组织级异常**（长期积累信号）
   - 如果同一账户下有多个 cookie 呈现高度一致的使用签名（都经过同一 clewdr 实例的标准化），可能在周/月级别被关联
   - 贡献：5-10 分（需要长时间积累）

4. **主动探测**（仅在分数越过 CHALLENGE 阈值时触发）
   - 在严格模式下被动分数 < 20，远低于 CHALLENGE 阈值 40
   - 因此主动探测几乎不会被触发
   - 贡献：N/A

**诚实结论：在红队最优配置下，蓝队的检出率低于 15%。这是我们必须接受的现实。**

### 4.3 红队最让蓝队头疼的反制策略

按头疼程度排序：

1. **"绕过 model-family" 建议（第四轮）** -- 这是最致命的一击。model-family 链路引入的 30% 检出权重，通过简单地消除中间层就能归零。MLP 系列规则全部失效。蓝队在此毫无还手之力。

2. **严格模式（1 cookie : 1 用户）** -- 直接消除了多用户行为聚合这一 45% 权重的检出维度。虽然代价是反代失去了经济意义，但从纯技术角度看，蓝队确实检测不到。

3. **clewdr 硬编码指纹** -- 通过代码审计确认，clewdr 在请求层面的指纹伪装（UA、headers、beta、API version）都是硬编码的，model-family 的头部不会透传到 Claude API。REQ 层规则几乎全部失效。

4. **API 状态机初始化序列模拟（第四轮新增）** -- 补齐了之前完全暴露的 BEH-07 维度。从 60-70% 检出率降至 20-30%。

5. **时序整形的四状态机** -- ActiveCoding / Thinking / LongBreak / Offline 四状态的概率转移，在严格模式下生成的请求间隔分布与真实用户几乎不可区分。

## 六、攻防的长期均衡与终局判断

### 6.1 均衡状态

经过五轮攻防，均衡点已经清晰：

**蓝队无法实现 100% 检出。稳态检出率：**
- 多用户共享场景：50-70%（蓝队核心战场）
- 单用户 RP 场景：40-55%
- 单用户编程场景：5-15%（蓝队投降区）

**红队无法实现 0% 检出。稳态存活率：**
- 严格模式 + 编程用途：85-95%（红队安全区）
- 严格模式 + RP 用途：45-60%
- 宽松模式（多用户共享）：30-50%

### 6.2 工程投入不对称性

| | 蓝队 | 红队 |
|--|------|------|
| 初始建设 | 7-10 人月 | clewdr 已有基础，增量 2-3 人月 |
| 持续运维 | 0.5 FTE + 基础设施 | 版本追踪 + cookie 采购 + 住宅代理 |
| 每次 Claude Code 更新 | 1-2 天指纹采集 | 1-2 天指纹更新 |
| 规模效应 | **有利**：同一系统保护所有用户 | **不利**：每个反代实例独立运维 |

**关键不对称：** 蓝队的检测系统建设一次，保护全部用户；红队的每个运营者都需要独立维护完整的防御栈。即使蓝队的检出率只有 50%，长期运营的成本不对称也会逐步淘汰非专业运营者。

### 6.3 终极武器：经济学而非技术

蓝队的终极武器不是任何一条技术规则，而是**经济学压力**：

1. 检测系统迫使红队采用 1:1 模式 → 反代失去共享经济性
2. 每个"用户"需要独立 cookie ($200/月) + 住宅 IP ($50-200/月) + 有限额度 → 成本趋近正规订阅
3. 反代运营者需要持续投入版本追踪、指纹更新、架构维护 → 运维成本远超正规使用
4. cookie 随时可能被封 → 不确定性风险溢价

**当反代的总成本（cookie + IP + 运维 + 风险）超过正规订阅的 70% 时，理性用户会选择正规订阅。** 这是蓝队真正不可攻破的壁垒 -- 它不依赖任何具体的技术检测规则，而是通过检测压力改变了反代的经济模型。

### 6.4 给 Anthropic 的最终建议

1. **优先部署 MVP（BEH-06v3 + USAGE-01）。** 仅这两条 P0 规则就能在 2-4 小时内检出 50% 以上的多用户反代，成本极低。

2. **不要追求 100% 检出率。** 单用户 1:1 模式的反代在技术上不可检出，但它也不构成重大商业威胁（1:1 模式下反代无利可图）。

3. **Rate Limiting 仍然是基线。** 即使没有复杂的行为检测，合理的 per-token rate limit（如 Anthropic 已有的 token 速率限制）就能阻止最粗暴的滥用。

4. **考虑产品侧方案。** 最有效的反代对抗不是检测，而是让正规使用足够便利和经济。如果 Claude Code 提供更灵活的团队计划（如 5 人团队包 $800/月 vs 5 x $200 = $1000），很多反代用户会自然转为正规用户。

5. **保持攻防节奏。** 每季度一次内部红队演练，保持检测系统的有效性。反代技术在持续进化，检测规则也需要持续迭代。
