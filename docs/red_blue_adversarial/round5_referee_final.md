# 第五轮（终局）- 裁判最终报告

> 日期：2026-03-30
> 角色：裁判（Referee）
> 定位：五轮红蓝攻防对抗的最终裁决报告，可独立阅读

---

## 背景概要

本次红蓝对抗围绕一个真实案例展开：clewdr（一个 Rust 编写的 Claude API 反向代理）的用户在通过 model-family（Go 编写的多模型网关）中转请求时，约 20 小时内被 Anthropic 封禁 Cookie；而个人直连使用 clewdr + OpenClaw 的用户长期安全。

红队（攻方）代表反代开发者，目标是规避 Anthropic 的检测系统。蓝队（守方）代表 Anthropic 安全团队，目标是设计可靠的反代检测系统。裁判负责评估双方方案的真实可行性、判定攻防胜负、给出技术结论。

五轮对抗从基础的指纹伪装 vs 请求特征检测起步，逐步深入到行为画像、统计检验、API 状态机模拟、经济学分析，最终收敛于一个清晰的纳什均衡点。

## 一、最终方案评估

### 1.1 红队三层架构的可落地性

红队的最终架构从第四轮的七层精简为三层 + 基础设施层，符合裁判的建议。

| 层级 | 核心功能 | 落地评估 |
|------|---------|---------|
| Layer 1: 请求标准化层 | Header 硬编码、UA 伪装、JSON 序列化顺序控制、探针检测 | **已部分落地。** Header 硬编码和 UA 伪装在 clewdr 现有代码中已实现（`constants.rs`、`chat.rs`）。JSON 序列化顺序控制（IndexMap 替代 BTreeMap）和探针检测需新增约 350 行 Rust，工程量可控。 |
| Layer 2: 行为整形层 | Cookie 池管理、时序控制、使用量限流、API 状态机初始化 | **可落地但复杂。** Cookie 管理的基础在 `cookie_actor.rs` 已存在，需扩展绑定和限流逻辑。时序整形（四状态机）约 300 行纯算法代码。API 状态机约 200 行。总增量约 700 行，技术上无障碍，但状态管理的调试和持久化是工程挑战。 |
| Layer 3: 协议适配层 | OpenAI 兼容端点、SSE 流处理、错误恢复 | **已基本落地。** clewdr 的 `router.rs` 和 `middleware/claude/` 已提供 OpenAI 兼容端点和 SSE 处理。仅需增强 429 处理逻辑。 |
| 基础设施层 | 住宅代理、VPS、域名 | **独立于代码，用户自行配置。** |

**裁判结论：红队的三层架构在工程上是真正可落地的。** 总增量代码约 1200-1500 行 Rust，对于已有完整框架的 clewdr 项目来说是合理的工作量。关键路径在 Layer 2 的状态管理复杂度 -- 这决定了方案从"能跑"到"稳定运行"的差距。

### 1.2 蓝队检测系统的可部署性

蓝队的最终架构为六层评分引擎（REQ/BEH/CONTENT/USAGE/META/MLP）+ 五级决策（ALLOW/MONITOR/CHALLENGE/RESTRICT/BLOCK）+ 分阶段部署路线。

| 组件 | 部署评估 |
|------|---------|
| 实时评分引擎（嵌入 API Gateway） | **高度可行。** 规则引擎嵌入现有 Gateway，零额外网络跳转，P99 < 5ms。Anthropic 作为 API 提供商已有 Gateway 基础设施。 |
| Redis Cluster 实时状态 | **标准方案。** 滑动窗口计数器、请求间隔序列存储，Redis 是业界标准选型。 |
| Kafka + ClickHouse 离线分析 | **可行但非 MVP 必需。** Phase 2-3 部署即可，MVP 仅需 Redis + 内存评分。 |
| 不使用 ML 模型 | **正确决策。** 四轮攻防验证，统计检验 + 规则引擎足够，ML 的边际收益不覆盖运维成本。 |
| 分阶段部署（Phase 0-3，6 个月） | **节奏合理。** MVP 仅需 4 人月（BEH-06v3 + USAGE-01 两条 P0 规则），风险可控。 |

**裁判结论：蓝队的检测系统是可部署的。** MVP（两条 P0 规则 + Redis + 基础评分引擎）可在 2 个月内上线，仅需 2 名工程师。关键是蓝队务实地放弃了 ML 方案，选择了规则引擎 + 统计检验的路线，大幅降低了落地难度。

### 1.3 双方成本分析的合理性

**红队成本分析：合理。**

| 场景 | 红队估算 | 裁判校验 |
|------|---------|---------|

| 多用户 1:1 月成本/用户 | $30-50 + 运维 | 合理。但 Cookie 月损耗率 10-30% 的估算偏乐观，在蓝队完整部署后可能升至 20-40% |

## 二、攻防终局判定

### 2.1 最终赢家

**蓝队赢得了战略层面的胜利，红队赢得了战术层面的胜利。综合判定：蓝队微优。**

理由：

蓝队的胜利是结构性的 -- 通过检测压力将反代推入 1:1 模式，使其商业模型崩溃。这一胜利不依赖任何单一技术规则，而是检测体系整体产生的经济学效果。即使蓝队的检出率只有 50%（多用户场景），只要迫使红队采用 1:1 + 限流 + 复杂架构，反代的运营成本就趋近于正规订阅。这是不可逆转的。

红队的胜利是局部性的 -- 在单用户编程场景下，被动检测分数 16.2，远低于任何合理的 ALLOW 阈值（25 分）。蓝队承认此场景检出率 < 15%。红队的指纹伪装技术已经成熟到蓝队无法在不大幅提高误报率的前提下检出。

但战略胜利的权重高于战术胜利：**一个在经济上不可行的工具，即使技术上完美，也失去了存在的核心意义。** 反代的核心价值主张是"低成本多人共享"，蓝队成功摧毁了这一价值主张。

### 2.2 纳什均衡点

攻防的纳什均衡点已经清晰收敛：

```
蓝队最优策略：
  - 部署 MVP（BEH-06v3 + USAGE-01），仅需 4 人月
  - 不追求 100% 检出率，接受单用户 1:1 模式逃逸
  - 用检测压力作为"经济武器"，而非直接技术封杀

红队最优策略：
  - 严格 1:1 模式（每 Cookie 单用户）
  - 编程场景为主，规避 RP 高风险内容
  - 放弃 model-family 中转，clewdr 直连
  - 持续版本追踪（每 1-2 周更新一次）

均衡结果：
  - 蓝队检出率：多用户 50-70%，单用户编程 5-15%
  - 红队存活率：严格模式 + 编程 85-95%，宽松模式 30-50%
  - 反代定位：从"省钱工具"退化为"兼容性网关/访问层"
```

在此均衡点上，双方都没有单方面改变策略的动机：
- 蓝队降低阈值 -> 误报率激增，得不偿失
- 红队放松 1:1 限制 -> 检出概率骤升，Cookie 快速被封

### 2.3 永恒的攻防优势维度

**永远是攻方（红队）优势的维度：**

| 维度 | 原因 |
|------|------|
| 单用户行为画像 | 1:1 模式下行为与真实用户在统计上不可区分，蓝队受限于误报边界 |
| 请求格式指纹 | 硬编码覆盖所有 header/UA/beta，守方看到的与真实客户端完全一致 |
| Claude Code 版本碎片化的掩护 | 真实用户使用不同版本、不同配置、不同 OS，为攻方提供天然的隐身空间 |
| TLS/网络层的模糊性 | CDN、负载均衡、中间设备的噪声使网络指纹不可靠 |

**永远是守方（蓝队）优势的维度：**

| 维度 | 原因 |
|------|------|
| RP 内容语义 | 叙事句式、情感词密度、角色实体等深层语义特征不可能在反代层消除 |
| 多用户行为聚合 | 信息论极限：多个独立用户的请求熵天然高于单用户 |
| 经济学压力 | 每增加一条检测规则就增加红队一层成本，这是累积性的、不可逆的 |
| 规模效应 | 检测系统建设一次保护全部用户，红队每个实例独立运维 |
| 主动探测权 | 蓝队可以在 system prompt 中注入任意验证指令，红队只能被动应对 |

## 三、真实案例最终分析

### 3.1 封号原因排列（精确到技术点）

回到最初的问题：用户通过 model-family 中转 clewdr 使用 Claude API，约 20 小时被封号。而个人直连 clewdr 长期安全。

经过五轮攻防的所有知识积累，封号原因的最终排列如下：

| 排名 | 技术点 | 权重 | 详细说明 |
|------|--------|------|---------|
| **#1** | 多用户行为聚合 | 45% | model-family 作为多模型网关，将数十个下游用户的请求汇聚到少量 Cookie 上。请求到达模式呈泊松分布（CV ~ 1.0），与单用户的突发性长尾分布（CV > 2.0）截然不同。Session 指纹（system prompt 长度、tool 集合、语言特征）在 2 小时内呈现高度多样性。消费量远超单用户合理范围（可能 > 100k tokens/小时）。 |
| **#2** | model-family 引入的格式破坏 | 30% | model-family（Go 编写）将 OpenAI 格式请求转为 Claude 格式，过程中引入：(a) Go `encoding/json` 的字母序 JSON key 排序（Claude Code 的 JS 保持插入序），(b) OpenAI 特有字段残留（`frequency_penalty`、`logit_bias` 等可能未完全清理），(c) `content` 字段可能被转为纯字符串（Claude Code 使用 content block 数组），(d) HTTP 头部可能携带 Go HTTP client 特征。 |
| **#3** | API 调用模式异常 | 15% | 通过 model-family 的请求缺少 Claude Code 客户端的初始化序列（`GET organizations` -> `GET models` -> `count_tokens`），没有伴随流量（穿插的 `count_tokens` 调用），直接以高频 `POST /messages` 开始。 |
| **#4** | 消费量异常 | 10% | 多用户共享导致单 Cookie 的 token 消费量远超 Pro/Max 订阅的合理范围。2 小时滑动窗口内的消费量可能触发使用量异常检测。 |

**对照：为什么个人直连安全？**

个人直连 clewdr + OpenClaw 的用户长期安全，因为：
1. 单用户 -> 行为画像天然是单用户模式（CV > 2.0，Session 指纹一致）
2. clewdr 直连 -> 无 model-family 的格式破坏，clewdr 硬编码了正确的 header/UA
3. 单用户消费量 -> 在合理范围内
4. 仅缺少 API 状态机初始化 -> 但权重低（15%），且可能被蓝队系统的阈值容忍

### 3.2 如果用户重新开始

基于五轮知识，用户重新开始应遵循以下清单：

1. **消除 model-family 中间层**：直连 clewdr，或使用纯 TCP 代理（nginx stream 模块）做负载均衡。绝不使用会修改 HTTP 请求的中间层。这一条单独就能消除 30% 的封号根因。

2. **严格 1:1 模式**：每个 Cookie 只服务一个用户。如果需要多人使用，为每人准备独立的 Cookie。这消除 45% 的封号根因。

3. **配置住宅代理**：使用 Sticky Residential IP，避免数据中心 IP 的 ASN 检测风险。每个 Cookie 绑定固定出口 IP。

4. **控制使用量**：每小时 < 30k tokens，每日 < 400k tokens。避免消费量异常信号。

5. **及时更新版本**：Claude Code 更新后 48 小时内更新 clewdr 的 `constants.rs` 中的版本常量（`CLAUDE_CODE_VERSION`、beta header 等）。

6. **避免 RP 高强度使用**：RP 内容的语义特征（55-65% 检出率）是红队无法在代理层解决的。如有 RP 需求，控制频率或使用其他通道。

### 3.3 clewdr 和 model-family 各自需要改什么

**clewdr 需要改什么：**

| 优先级 | 改动项 | 工程量 | 效果 |
|--------|--------|--------|------|
| P0 | 文档中明确推荐直连部署，不推荐 model-family 中转 | 文档更新 | 消除 30% 封号根因的信息传达 |
| P0 | JSON 序列化顺序控制（IndexMap 替代 BTreeMap） | 50-100 行 | 消除 JSON key 排序的检测信号 |
| P0 | 自动化版本追踪（CI/CD 监控 Claude Code npm 发布） | 50 行脚本 | 缩短版本追踪窗口期 |
| P1 | RequestNormalizer（清理非标准字段、规范 system 格式） | 200 行 | 消除格式层面的所有检测信号 |
| P1 | 使用量限流（每 Cookie token 计数器 + 软限制） | 100 行 | 预防消费量异常检测 |
| P2 | API 状态机初始化序列 | 300 行 | 消除 BEH-07 检测信号 |
| P2 | 探针标签检测与移除 | 150 行 | 应对未来可能的主动探测 |

**model-family 需要改什么：**

| 改动项 | 说明 |
|--------|------|
| 透传模式 | 对 Claude API 的请求不做任何格式转换，直接透传上游 clewdr 构造的请求。包括 header、body、序列化格式全部透传 |
| 禁用 Go HTTP client 默认行为 | 确保不添加 Go 特有的 HTTP 头部（如 `Accept-Encoding: gzip` 的特定格式） |
| JSON 序列化 | 如果必须处理 JSON body，使用 `json.Decoder` 保持原始 key 顺序，而非 `json.Marshal` 重新序列化 |
| 或者（更好的选择）| 对 Claude API 后端使用纯 TCP 代理模式，不解析 HTTP 层 |

## 四、五轮对抗总结

### 4.1 每轮关键转折点

| 轮次 | 关键转折点 |
|------|-----------|
| **第一轮** | 蓝队建立了多层置信度评分模型，奠定了整个攻防的分析框架。红队的首轮防御较为被动，仅针对蓝队规则逐条修复。蓝队 7.5 vs 红队 6.5，蓝队领先。 |

| **第五轮** | 双方交付可落地的最终方案和经济学分析。红队诚实承认经济壁垒不可攻破。蓝队诚实承认单用户场景检出率 < 15%。攻防收敛到纳什均衡点。 |

### 4.3 最有价值的技术洞察 Top 5

**#1 -- 经济学是终极武器，技术只是手段**

蓝队不需要 100% 检出率。只要检测压力迫使反代采用 1:1 模式 + 限流 + 复杂架构，反代的运营成本就趋近于正规订阅，经济模型崩溃。这一洞察将整个攻防从"技术可行性"推向了"经济可行性"，是五轮对抗中最深刻的发现。

**#2 -- 多用户行为聚合是不可完美伪装的（信息论极限）**

多个独立用户的请求在统计上天然具有更高的熵和多样性。即使红队做了时序整形，Session 指纹（system prompt 长度、tool 集合、语言特征）仍然可以跨请求关联。唯一的解法是 1:1 -- 但这本身就是蓝队的胜利。这是信息论层面的根本限制。

**#3 -- 中间层（model-family）是最大的检测放大器**

真实案例中 30% 的封号权重来自 model-family 引入的格式破坏。这个发现的价值在于：很多用户以为问题出在 clewdr 的指纹伪装不够完美，实际上 clewdr 的指纹已经足够好，是中间层把它破坏了。红队"绕过 model-family"的建议用最低成本解决了最大的单一风险因素。

**#4 -- 误报边界是守方不可逾越的天花板**

蓝队的检测阈值不能任意降低。真实 Claude Code 用户使用不同版本、不同配置、不同 OS，存在自然的行为多样性。当红队在单用户严格模式下的被动检测分为 16.2 时，蓝队要把阈值降到 16 以下就会导致大量正常用户被误触发。这个"误报边界"保护了红队的生存空间。

**#5 -- 内容是最后的不可伪装信号**

在请求层指纹完全伪装、行为画像通过 1:1 模式消除的情况下，请求内容本身成为蓝队唯一的持续信号。RP/创意写作内容的语义特征（叙事句式密度、情感词、角色实体）是反代架构层面无法消除的 -- 除非对内容做深度改写，但这会改变语义、损害用户体验。这说明在足够精细的检测下，"你发什么"比"你怎么发"更重要。

### 4.4 最意外的发现

1. **个人使用反而安全**：直觉上，更精密的反代（如 clewdr）面临更高风险。但真实案例表明，个人 + clewdr 直连长期安全。封号的根因不是 clewdr 的指纹不够好，而是多用户共享 + 中间层破坏。这颠覆了"检测主要靠识别反代软件指纹"的假设。

2. **蓝队主动选择不用 ML**：在 AI 时代，蓝队最终决定不使用 ML 模型进行检测，而是坚持规则引擎 + 统计检验。理由是 ML 的边际 recall 提升不覆盖训练数据偏差、模型更新延迟、解释性差等成本。这是反直觉但正确的工程决策。

3. **红队自己承认反代的经济不可行性**：红队在终局报告中明确写道"反代作为商业模式是不可行的"，将反代的定位从"省钱工具"调整为"兼容性网关"。攻方主动承认守方的战略胜利，这在攻防演练中不常见。

4. **JSON key 序列化顺序成为检测信号**：Go 的 `encoding/json` 按字母序排列 key，JS 保持插入序，Rust/serde 取决于底层数据结构。这个看似无关紧要的实现细节成为了蓝队的有效检测信号（MLP-03）。这提醒我们，在指纹伪装中，"魔鬼在细节里"。

## 六、给项目的最终建议

### 6.1 给 clewdr 的 Top 5 改进建议

| 优先级 | 建议 | 效果 | 工程量 |
|--------|------|------|--------|
| **1** | **在文档和 README 中明确推荐直连部署，标注 model-family 中转为"不推荐"** | 消除 30% 封号根因的用户教育 | 文档更新，1 小时 |
| **2** | **JSON 序列化顺序控制：审计 serde 配置，确保使用 `IndexMap` 或自定义序列化保持插入序** | 消除 JSON key 排序的检测信号 | 50-100 行代码 |
| **3** | **RequestNormalizer：在请求发送前清理所有非 Claude Code 标准字段，规范 system prompt 格式** | 消除格式层面的所有检测信号，对下游兼容性更好 | 200 行代码 |
| **4** | **使用量限流：每 Cookie 的 token 计数器 + 每小时/每日软限制，超限时返回 429 给下游** | 预防消费量异常检测，保护 Cookie 寿命 | 100 行代码 |
| **5** | **自动化版本追踪：CI/CD 或 GitHub Action 定期检查 Claude Code npm 发布，发现更新自动创建 Issue** | 缩短版本追踪窗口期，降低运维人力 | 50 行脚本 |

### 6.2 给 model-family 网关的 Top 5 配置建议

| 优先级 | 建议 | 说明 |
|--------|------|------|
| **1** | **对 Claude API 后端使用纯 TCP 代理模式（stream 模块），不解析 HTTP 层** | 从根本上消除格式破坏。如果 model-family 只做路由不做格式转换，所有 MLP 系列检测信号都不存在 |
| **2** | **如果必须做格式转换，使用流式 JSON 解析器（如 `json.Decoder`）保持原始 key 顺序** | 避免 `json.Marshal` 重新序列化导致的字母序 key 排序 |
| **3** | **不添加任何自定义 HTTP 头部（X-Forwarded-For、Via 等），禁用 Go net/http 的默认行为** | 防止 Go HTTP client 特征被检测 |
| **4** | **对 Claude API 后端不做任何字段增删，完整透传上游 clewdr 构造的请求体** | 包括 `metadata`、`system`、`anthropic-beta` 等字段全部透传 |
| **5** | **考虑为 Claude API 后端提供"raw proxy"模式的配置选项** | 让用户可以选择对特定后端禁用所有请求处理逻辑，只做连接级别的转发 |

### 6.3 给用户（使用者）的 Top 5 使用建议

| 优先级 | 建议 | 理由 |
|--------|------|------|
| **1** | **严格 1:1 模式：每个 Cookie 只给自己用，不共享** | 共享是 45% 封号根因。1:1 模式下被动检测分 < 20，蓝队几乎无法检出 |
| **2** | **直连 clewdr，不通过 model-family 或其他 HTTP 中间层** | 中间层是 30% 封号根因。如需多模型路由，在 clewdr 上游使用纯 TCP 代理 |
| **3** | **配置住宅代理（Sticky Residential IP），避免使用数据中心 IP** | 数据中心 IP 的 ASN 检测是一个低成本但有效的信号。住宅 IP 与正常用户无法区分 |
| **4** | **控制使用量：每小时不超过 30k tokens，每天不超过 400k tokens** | 消费量异常是蓝队的 P0 检测规则之一。控制在合理范围内可避免触发 |
| **5** | **关注 clewdr 的版本更新，及时升级** | Claude Code 版本追踪是持续性的运维需求。使用过时版本会在窗口期内暴露（40-60% 检出率）。升级 clewdr 等于更新指纹 |
